# Critic result — TESTABILITY lens

Reviewed `DESIGN_SPEC.md` only (per instructions), cross-checked claims against `src/` and `docs/` where the spec cites existing machinery (`fit_two_way`/`pool_random_effects` in `src/physics/layer2/pooling.py`, `driver_utility.py` #628, `mixture_stability.py`/`f12_held_out_stability.py` #625 Gate 3, `RegulationEra.for_season`).

| ID | Lens | Severity | Finding | Disposition | Reason |
|---|---|---|---|---|---|
| T1 | testability | BLOCKING | Grip module G's only named validation (§2, line 76 / Testing pathways line 131) is in-sample self-scoring: G is fit from field-pooled pace (compound/tyre-age/fuel corrected), then "validated" by checking whether subtracting that same G reduces reconciliation error on the same kind of pace variation it was fit against. No held-out split is named (e.g. fit G on a subset of laps/drivers, score reconciliation on a disjoint subset). G has two free-form fit surfaces per weekend (a saturating intra-session curve + a free per-session offset) — with that much freedom, near-arbitrary G will improve in-sample reconciliation error just by absorbing noise, so "subtracting G worsens reconciliation" can only fire on a badly broken fit, not a subtly wrong one. This is exactly the failure mode the critic brief calls out: a subtly-wrong implementation (wrong functional form, misplaced offset) passes the named gate by construction. | | |
| T2 | testability | MAJOR | The offset/curve identifiability problem is unaddressed: "free offset per session start, estimated from data" (§2) plus an intra-session saturating curve fit in the same pass creates a classic aliasing risk — the curve's initial value and the offset are not separably identified from pace data alone unless the fit is constrained or cross-validated against an independent signal. No test is named to check the two are actually separable (e.g. synthetic-data recovery test with known ground-truth offset+curve, or an out-of-sample check that the offset doesn't just absorb curve-shape error). Without it, "σ(G) propagates to every consumer" (line 75) propagates an uncertainty estimate that could be structurally understated. | | |
| T3 | testability | MAJOR | Two of the three named "machine-checkable invariants" for SegmentMap are tautological given how the map is constructed, not substantive correctness tests: (a) "tiling completeness (every meter typed exactly once)" is guaranteed by any implementation that partitions distance-into-lap by construction — it cannot detect a corner mis-typed as straight, only a gap or double-cover; (b) "nesting exactness (segment sums = sector spans)" (line 130) is likewise guaranteed by the split-not-snap rule itself (§1 line 61: sector lines are mandatory cut points) — any implementation that respects that rule passes trivially, independent of whether the corner/braking/straight *typing* inside those spans is physically correct. Neither test exercises the actual classification logic (the v_ref²×curvature threshold, the p5–p10 brake-onset quantile) against any ground truth. | | |
| T4 | testability | MAJOR | The braking-zone gate is specified as a *range*, not a fixed value — "robust low quantile p5–p10, never mean" (§1 line 59) — with no test pinning down which quantile is used or bounding how much the resulting boundary moves across that 2x range. Contrast with this repo's own F12 precedent (`mixture_stability.py`), which fixes `LOG_RADIUS_SCALE`/`LATERAL_G_SCALE`/`F12_AGREEMENT_THRESHOLD` as named constants chosen *before* the real-data run specifically so the gate can't be tuned post-hoc. §1 has no analogous frozen constant, so two conforming implementations picking p5 vs p10 could disagree materially on segment boundaries with neither one failing any named test. | | |
| T5 | testability | MAJOR | §3's "internal composition" test ("segment deficits sum to lap deficit," Testing pathways line 133) is the same class of tautology as T3: if segment deficits are computed as an additive decomposition of the lap deficit, they sum to it by construction (floating-point precision check at best), and a wrong per-segment allocation between classes still passes as long as the total is preserved. It cannot catch, e.g., systematic misattribution between corner-class and braking-zone deficits. | | |
| T6 | testability | MAJOR | The fingerprint's headline test — "residual split-half replication with support-count-scaled expectations" (Testing pathways line 134) — names no threshold, no functional form for "support-count-scaled," and no commitment to freeze it before looking at real data. This is the single most load-bearing correctness check in the spec (it's what the join's honest-σ claim rests on) and it is the *least* specified quantitatively, again by contrast with the F12 gate elsewhere in this same codebase, which the spec cites approvingly (line 60, 132) but does not hold §4 to the same discipline. As written, a post-hoc threshold pick could bless a fingerprint that doesn't actually replicate. | | |
| T7 | testability | MAJOR | The join's only named test — "does fingerprint×composition beat driver-overall-only prior … falsifiable per weekend" (Testing pathways line 135) — is an *outcome-level* comparison, not a correctness check of the join mechanism (soft-membership weighting, σ propagation, class-vocabulary alignment). A join with wrong per-class weights, a sign error in a subset of cells, or wrong σ-widening for thin cells can still beat the driver-overall-only baseline on average (compensating errors: overall-skill signal dominates, per xR3's own finding line 38) while being mechanistically broken. No unit-level invariant is named for the join arithmetic itself — e.g. "join reduces exactly to driver-overall mean when composition is uniform across classes" or "join returns a driver's constant cell value when all their cells are equal, regardless of composition vector" — the natural reduces-to-simple-case tests that would catch an implementation bug independent of whether the physics signal is real. | | |
| T8 | testability | MINOR | Internal contradiction on what kind of test the join and fingerprint checks are: §7's header states the instrument panel is explicitly "sizing, never go/no-go" and the Kill condition (line 24) states no result routes to abandonment — yet the Testing pathways section calls the join test "falsifiable per weekend" (line 135) and lists an explicit fail condition for G (line 131) and the class ladder (line 132). A test whose failure triggers no defined action (per the no-kill-condition ruling) is a measurement, not a falsifiable gate in the ordinary sense; the spec uses "falsifiable" language for both kinds without distinguishing which named tests have consequences and which are purely diagnostic. A reader implementing Build 1's exit criteria cannot tell, from this document alone, which of the seven Testing-pathway bullets block progression to Build 2 and which are read-only. | | |
| T9 | testability | MAJOR | §4's reuse claim — "the hierarchy … falls out of the EXISTING `fit_two_way` pooling primitive with axes reinterpreted as driver×class, completed by `pool_random_effects`" (line 96) — doesn't match what's actually in the repo. `fit_two_way` (`src/physics/layer2/pooling.py:172`) is a two-way crossed decomposition (team × circuit) using method-of-moments variance components that the module's own docstring calls "exact for a balanced grid, approximate otherwise" (line 173). The existing driver-facing precedent this spec is building on, #628's `driver_utility.py`, does *not* use `fit_two_way` at all — it pools per-`(driver, axis)` groups directly through `pool_random_effects` with no crossed second axis. Driver×class cells will be far from a balanced grid (some drivers have thin support in rare corner classes; class counts vary by circuit mix across a season) — exactly the regime where `fit_two_way`'s own docstring flags its variance-component estimates as approximate. No test is named to check the two-way decomposition's shrinkage behavior holds up under this realistic imbalance (e.g. a synthetic-recovery test with known ground-truth driver/class effects and deliberately unbalanced cell counts), and reusing untested code for a genuinely new statistical regime (new axes, new imbalance profile) is being sold as "zero new statistical machinery" when it is, in fact, a new application whose correctness on this specific data shape is unverified. | | |
| T10 | testability | MINOR | Sample-size sufficiency for the per-era F12 gate (§1 line 60, extended by reference to class-ladder stability) is asserted but not checked against what Build 1 actually has: Build 1 runs 2023-first (§8 line 122) and rules-eras are coarse (multi-year spans, e.g. 2022–2025 as one era per this repo's `RegulationEra`). A held-out-circuit stability gate needs enough within-era circuit diversity to make 50/50 circuit-name splits meaningful (the real F12 script draws from a full multi-year `grip_bin_obs` table); it's not stated whether 2023-only data gives enough circuits per era to run this gate meaningfully at Build 1's stated scope, or whether the era-gate is silently deferred until backfill (line 122's "chased after the panel proves the machine") — which would mean the ladder that gates §1's class vocabulary is unvalidated during the very build the instrument panel is supposed to steer. | | |
| T11 | testability | MINOR | The composed-sector scorecard (§7 line 117 / Testing pathways line 136) conflates two different claims under one bullet without separating their falsification conditions: (a) segment *positions* summing to sector spans, which is geometrically guaranteed by construction (T3/T4's point) and (b) predicted sector *times* validated against official FIA sector times, which is the genuine external, non-self-referential check ("the one external sub-lap anchor," line 136 — correctly identified as such). The spec should name (b)'s calibration-coverage criterion explicitly (e.g. what coverage percentage at what confidence level counts as pass) the same way it's willing to do for F12's threshold, rather than folding a real external test and a construction tautology into one undifferentiated bullet. | | |
