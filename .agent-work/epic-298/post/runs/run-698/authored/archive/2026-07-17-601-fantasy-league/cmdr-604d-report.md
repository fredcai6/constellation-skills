## The recommended seam + rejected alternatives (what the Admiral surfaces to the human)

**3 candidates were generated by independent parallel subagents** (Agent tool, Sonnet, one named
constraint each, no cross-visibility between them), then converged to one recommendation by me,
then the converged doc was reviewed by a 4th, independent cold-critic subagent with **no
authoring context** (handed only the drafted doc + mission frame).

**Recommended: Candidate C — hybrid, staged pipeline with checkpoint files.**
`scripts/race_week.py` (thin CLI) + a small library core (e.g. `scripts/race_week_stages.py`),
kept at `scripts/`-level (not a new `src/` architecture region, matching the existing
`collect_evo_data.py`/`run_sampled_runtime_comparison.py` convention). Four stages
(`collect-check` / `predict` / `optimize` / `explain`), each reading the prior stage's checkpoint
from `outputs/race_week/<year>/<round>/` and writing its own (`01_sessions.json` /
`02_prediction.json` / `03_lineup.json` / `04_explainer.md`); resumption via a content hash on
each checkpoint. The ranked top-10 (`03_lineup.json`) is durably on disk **before** the explainer
stage even runs, so the hard/soft gate split is enforced by construction (a file exists or it
doesn't), not by exception-handling discipline inside one process.

**Rejected — Candidate A (wraps-existing-CLI, no checkpoints).** Simplest to build and would be
the right minimal choice for a single-shot, same-session command — rejected specifically because
the sprint/Fri-Sat-incremental-landing requirement makes cross-invocation resumability a real,
not speculative, need; a single-process design either re-polls DB state cheaply each time (fine)
or wastes a full predict+optimize cycle on every re-invocation when nothing usable has changed
(the actual cost, not "durability," which A could also get cheaply — see the critic finding
below).

**Rejected — Candidate B (new `src/race_week/` first-class module, in-memory state machine).**
Best testability of the three in isolation, but its proposed `RaceWeekState` (expected sessions,
landed flags, stage status, hard/soft gate flags) is exactly the information Candidate C already
persists as checkpoint files — to survive the real Friday-to-Saturday gap (this is a
local/single-operator tool, no long-running service), B's state would need on-disk serialization
anyway, at which point it has re-derived C's mechanism while also paying the cost of a new
map-visible `src/` package. Not an Honest-Null (B is not wrong) — dominated: C gets the same
durability property at lower structural cost.

**Open item explicitly NOT resolved by this document (Wave 2's to decide):** whether Candidate A's
minimal shape (no checkpoint/hash machinery, just `01_sessions.json`-style partial polling) is
actually sufficient once a real predict+optimize runtime is benchmarked — the idempotency argument
for full checkpointing is asserted, not measured, and the design doc says so explicitly.

## Cold-critic verdict (the real value-add this run)

The independent critic (fresh context, doc + mission frame only) found: 1 blocking, 5 significant,
several minor findings. It **independently re-verified all 7 originally-cited signatures against
source and found zero mis-citations** — but caught things my authoring pass missed:
- **The `sampled-predict --db-path` default-vs-per-year-write divergence** (verified myself
  against source post-critique — genuinely serious, would have broken Wave 2's first real run).
- The explainer's actual content-generation source was never named (I'd conflated
  `generate_report`'s existing Markdown twin with a supposedly separate new artifact).
- My "checkpoint durability beats exception-handling" argument for recommending C over A only
  actually required "write JSON to disk before attempting the explainer" — A could do that too,
  without any checkpoint machinery; I revised the recommendation's justification to rest on
  idempotent partial-state tracking instead (explicitly flagged as unmeasured).
- An internal-consistency issue (I described C as having "no fan-out" while penalizing B for
  identical call-graph coupling — fixed).
- `--sampled-runtime-manifest` provenance, partial-FP semantics into predict, and concurrent-
  invocation handling are named as open Wave-2 questions rather than silently assumed.

All of the above are now addressed in `docs/design/race_week_seam.md`'s "Known Limits / Open
Questions" section and the revised recommendation text — the document was NOT shipped as
originally drafted.
