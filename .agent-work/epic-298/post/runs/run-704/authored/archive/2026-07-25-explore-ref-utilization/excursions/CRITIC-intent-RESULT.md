# Critic result — lens: intent-fit

Cold adversarial review of `DESIGN_SPEC.md` only (no board, no logs, no excursion files read). Source code under `src/` and `docs/` consulted to check claims against reality where noted.

| ID | Lens | Severity | Finding | Disposition | Reason |
|---|---|---|---|---|---|
| I1 | intent-fit | BLOCKING | The Intent's opening sentence ("Reformulate physics→prediction as a decomposition, **not a feature injection** ... replacing raw classification positions that entangle car, driver, and luck") is contradicted by the design's own stated integration mechanism. Design principle 5 says "physics enters prediction as a family of candidate features; NN reliance on them is the success signal." §4's convergent-outcomes bullet says "evo reaches this module only through a thin config-gated adapter (the `physics_feature_injection` pattern)." §8 Build 3 describes the endpoint as "physics feature family → fusion choir (Phase-6 seam, (μ,σ) payload)." All three point at the same real, already-existing module — `src/evo_predictor/physics_feature_injection.py` — which builds one `ModuleFieldResult` ("driver_quali_power_from_physics_feature_view") that flows into `fuse_module_fields_ordered`'s precision-weighted fusion alongside the 12 production neural modules (per CLAUDE.md's own architecture notes). That is a feature injection by any reasonable reading of the term — one more candidate signal competing for weight in an existing ensemble. Meanwhile "Any change to the existing 12 neural modules or their training in Builds 1–3" is explicitly Out of Scope, and those 12 modules are trained against `session_classifications` (raw positions) throughout — so nothing in this spec, across Builds 1–3, actually replaces raw classification positions as a training target or truth channel. The Intent's headline claim about *what kind of change this is* is the opposite of what the design's own later sections and the existing code describe. | | |
| I2 | intent-fit | MAJOR | The "done feels like" promise that "the instrument panel reporting the size of every signal... so subsequent builds are steered by measurement instead of hope" has no mechanism attached anywhere in the document. §7 states the panel is explicitly "sizing, never go/no-go." The kill condition is "none at the frame level, by owner ruling," and fingerprint non-replication "routes to more structural work... never abandonment." §8's build sequence (Build 1 → Build 2 → Build 3) states no threshold, branch point, or decision rule keyed to any §7 output. As written, Builds 2 and 3 proceed regardless of what the instrument panel measures in Build 1 — there is no path by which a weak variance-decomposition result or poor sector calibration changes what gets built next. "Steered by measurement instead of hope" is asserted, not designed. | | |
| I3 | intent-fit | MAJOR | Intent names "the live sampled predictor" as the primary beneficiary ("for whom"), but Build 1 — the thing this spec actually confirms — delivers nothing reachable by it. Out of Scope item 1 explicitly defers "wiring any of this into live predictions by default (fusion entry stays toggle-gated, critical-eye evaluated)," and per Build 3's own framing that gate persists even at the point of eventual integration. Every artifact in the "done feels like" list (segment maps, grip baseline, utilization store, fingerprints, join, instrument panel) is upstream physics-store construction with no consumer in the live prediction path within this spec's scope. The stated primary beneficiary is not served by what this document confirms; the payoff is deferred past Build 1, Build 2, and arguably past Build 3's own gating language. | | |
| I4 | intent-fit | MAJOR | The headline framing "Car = reference; driver = utilization" pitches a clean, symmetric two-term decomposition as the core value proposition, but the spec's own exploration record undercuts that symmetry without the design addressing the gap. xR2 found "literature does not converge on a car/driver split (61–88% constructor)... nobody models lap time; no prior art at our granularity." xR3's golf analog found residual "shape fit" had **zero out-of-sample power** after controlling for overall skill, and the spec explicitly says "expect our interaction term small." §4 then builds the driver side as hierarchical-shrinkage cells with "thin cells → fat σ" — i.e., the design already anticipates a thin, uncertain driver signal. If the driver-utilization term is expected (by the spec's own gathered evidence) to be small and heavily shrunk, the document never confronts what that implies for the central "car=reference, driver=utilization" pitch as an improved truth channel — the exit gate (§7) measures the *size* of the driver share but nothing in Build 1 asks or answers whether a small, fat-σ driver term is actually worth the store/fit/join machinery built around it. | | |
| I5 | intent-fit | MINOR | Intent names "the fantasy-league decision layer" as a second, "ultimately" beneficiary, but no build (1, 2, 3) or the roadmap tail names any connection to `src/fantasy_scoring/` or the fantasy-pts-per-race decision metric that CLAUDE.md records as the project's actual north-star metric. The claim is asserted in Intent and never designed for anywhere in the document — it reads as scope-creep framing with no corresponding commitment. | | |
| I6 | intent-fit | MINOR | Intent's "done feels like" list includes "the join producing weekend priors" without flagging that Build 1 is quali-side only (§8: "Build 1 (quali-side, 2023-first)"). A reader taking Intent at face value would expect race-inclusive weekend priors from the confirmed scope; the race-side join doesn't exist until Build 2 (§5/§8), which this spec only rules the interface for, not the build. | | |
