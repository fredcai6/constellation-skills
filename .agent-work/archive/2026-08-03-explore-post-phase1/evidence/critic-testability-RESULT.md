# Critic result — testability

Lens: can each pathway in the design be exercised and falsified?
Source: `DESIGN_SPEC.md` only, read cold. Disposition and Reason are left empty for human triage.

| ID | Lens | Severity | Finding | Disposition | Reason |
|---|---|---|---|---|---|
| T1 | testability | BLOCKING | Workstream C's acceptance test names no sample size and no pass criterion. It says a cold agent given only the engine channel performs the behavior and the no-instruction arm does not, but exc-8 ran each arm once, and the spec adopts that same protocol as the standing acceptance test. Agent behavior is stochastic, so a one-run arm cannot separate signal from noise, and the test has no defined failure: if three of five agents perform the behavior, nothing in the spec says whether the tranche passed. Fix by naming n per arm and the pass threshold before any relocation ships. | | |
| T2 | testability | BLOCKING | Workstream C's token guard measures the wrong denominator. The spec's guard is "if total delivered tokens per `current` call grows"; the quantity that decides whether relocation pays is tokens per run. Always-loaded prose is paid once per context, while a relocated imperative is paid on every `current` call at that gate. Nobody has measured how many times `current` is called per gate on a real run, so relocation can raise total delivered tokens while passing the stated per-call guard and while the always-loaded word count shrinks as required. Fix by measuring `current` call frequency per gate first, and by making the acceptance measurement per-run. | | |
| T3 | testability | BLOCKING | Workstream F's separation test is arranged around the failure it should be probing. exc-9 observed that a dispatched subagent inherits the parent's server and presents as one session, which breaks lease identity and hands the subagent the parent's context reading. The stated test drives a parent and a subagent through two different server instances, so it exercises the configured-happy path and presupposes the per-dispatch config generation that ruling 1 leaves unsettled. Nothing falsifies the observed inheritance path. Add a test that dispatches a subagent with no special configuration and asserts the system refuses or fails closed rather than silently serving the parent's identity. | | |
| T4 | testability | BLOCKING | Workstream A's stale-binding sweep has no test pathway at all, and its stated liveness mechanism cannot apply to the population it must retire. The sweeper is justified by "once keys are per agent, a script can test each key's liveness against its own transcript" — but the 47 accumulated bindings are pre-migration and keyed by bare `session_id`, so by construction they have no per-agent transcript to test against. exc-6 also lists this migration as untested. The spec's Testing pathways section says nothing about the sweeper. This is a one-shot destructive script against live state with no dry-run, no rollback, and no falsifier. Name the liveness test that works on bare-`session_id` keys, or state that the 47 are retired unconditionally, and give the run a dry-run mode with a recorded before-state. | | |
| T5 | testability | MAJOR | No pathway in workstreams A, C, or F becomes a repeatable regression test. Every one of them is a live-fire demonstration requiring dispatched cold agents, and the spec never says which tests are automated, who reruns them, or what runs on change. Only B and D produce anything a suite could hold. The consequence is that #383's zero-readings symptom, once fixed, has nothing standing between it and silent return, and the same is true of the relocation channel that C's value depends on. Name, per workstream, which assertions become automated checks and which are accepted as one-shot manual evidence. | | |
| T6 | testability | MAJOR | Workstream A tests the wrong failure. The stated fail-closed test feeds an unresolvable identity and asserts nothing is written, but the dangerous outcome is a reading attributed to the wrong agent, and the acceptance criteria give no mechanism for establishing ground truth about which agent produced which record. With several agents on the same model, a misattributed reading is indistinguishable from a correct one by inspection. The one case that produces misattribution — the identical-command race — is deferred on the claim that it fails closed by design, which exc-6 lists as untested. A design cannot defer the test for a case on the strength of the untested claim about that case. Make agents distinguishable by construction in the test, and pin the race before deferring it. | | |
| T7 | testability | MAJOR | Workstream A depends on harness version 2.1.220 or later for per-subagent transcripts, and nothing tests or detects that dependency. On an older harness the transcripts do not exist, identity never resolves, and under the fail-closed invariant the governor writes nothing — which is exactly the #383 symptom the workstream exists to remove, now with a different cause and no signal distinguishing the two. Add a version or capability probe that reports which mode it is in, and an assertion that the acceptance run actually took the per-agent path. | | |
| T8 | testability | MAJOR | Two workstreams are gated on probes whose negative branch is unspecified, so neither can be scheduled or falsified as written. Workstream A says to check the real PostToolUse hook payload first: if it carries the subagent's transcript path the change is roughly one line, otherwise the structured matcher ships — the difference between one line and a lifted 250-line module, with no stated handling for a payload that carries neither shape. Workstream F says to check first whether an interactive session picks up a fresh `.mcp.json` without a restart, and states no fallback if the answer is no, though per-dispatch config generation is the candidate answer to ruling 1. Record each probe's outcomes and the design each outcome selects, so the probe result is a decision and not a surprise. | | |
| T9 | testability | MAJOR | Workstream B fixes two instances but leaves the class untested. The unrendered `anchors` and `constraints` blocks were found by five cold agents hitting them independently, not by any test, because no test asserts the contract that `current` is the complete state channel. Rendering those two blocks does nothing to prevent the next gate field that is added and never rendered. Replace the instance fix with a completeness property: enumerate the fields a gate may carry and assert every populated one appears in the projection. That test falsifies the class; a golden diff does not. | | |
| T10 | testability | MAJOR | The RAIL echo removal is treated as a pure token change and its behavioral effect is never tested. The doubled imperative may be load-bearing for compliance — repetition is one of the few levers that raises the odds a model follows an instruction — and workstream C's entire value rests on agents reliably acting on an imperative delivered once through this now-de-duplicated channel. The stated B test is a golden-output diff, which cannot see compliance. Since C's tracer runs against the post-B channel anyway, state that dependency explicitly and treat a compliance drop in C as evidence against B rather than against the tranche. | | |
| T11 | testability | MAJOR | Workstream C's selection authority is presented as measurement but is single-rater hand classification. The census is described as hand classification over 97 units, "reproducible with the prototype's census script" — the script can reproduce counts, not the judgment calls that produced the classes — and 54.2% and 84% inherit whatever one excursion agent decided. The rule "rules that span more than one gate stay" is the boundary that matters most and has no mechanical detector. A unit misclassified as gate-specific gets relocated and stops being delivered at the other gates that needed it, and the gate-level acceptance test cannot see that. Add a second independent classification of at least the units in the tranche, or a check that a relocated unit's text is not referenced by another gate. | | |
| T12 | testability | MAJOR | Workstream C's test verifies "the behavior", singular, per gate, while the tranche relocates many paragraph-level units into the execute and plan imperatives. Nothing requires each relocated unit to be traced. A ten-paragraph imperative can pass a gate-level test on one salient behavior while nine other relocated behaviors are silently dropped — and that is precisely the dose-response failure the spec names as unknown. Require a named observable per relocated unit, or cap the tranche at the number of units you are willing to trace individually. | | |
| T13 | testability | MAJOR | Workstream D's #329 fix reintroduces the defect's own shape at a different granularity, and D's stated test does not apply to it. The fix is to wire the isolation script into "every template whose runs enter worktrees" — a prose predicate with no membership test, when the original defect was exactly an omission that `grep -rln` exposed. Nothing falsifies a template left out. Separately, D's test is "re-run the command that failed", which has no referent for #329: that command never ran at all, so there is no failing invocation to re-run. Add an enumeration check that lists worktree-entering templates and asserts each carries the precondition, and state #329's test as the deliberate-breakage negative test that D describes for the general case. | | |
| T14 | testability | MAJOR | Workstream D's #328 conversion names no command, so its acceptance test cannot be written. The two invariants are said to be documented as mechanically enforced and currently wired as `record()` surveys, and the fix is to rewire them as command checks — but the spec never says what command runs, what it inspects, or what its exit codes mean. Until that exists, "assert that the engine refuses" has nothing to assert against. There is also a routing risk the spec should settle: if no command can decide these invariants, the two-bin rule sends them to the named-human bin, and this workstream is the wrong home for them. Name the command and its failure condition, or reclassify. | | |
| T15 | testability | MAJOR | Workstream E has no defined done-condition and no content-preservation test. "The backlog should then read as about a dozen real work items plus the genuine standalones" cannot be evaluated — neither "about a dozen" nor "genuine" is checkable, so nobody can say whether consolidation finished. The one stated falsifier for consolidation is that a cluster item must link the singles it absorbed, which tests linkage, not that the absorbed content survived; a cluster issue can link twelve singles and carry none of their substance while passing. This runs against roughly a hundred issues in one direction. Capture a pre-consolidation snapshot of every issue body being absorbed, and state the numeric or query-shaped condition that means E is done. | | |
| T16 | testability | MAJOR | Two closeout items in workstream E are unfalsifiable as written, and one debt the spec itself identified lands nowhere. E says to "verify the epic #298 issue, then close it" without naming a single thing verification must assert — while exc-1 reports that #308 substituted a migration for the consolidation it was required to do, leaving that done clause unmet and untracked. So the spec closes the epic whose own audit found an unmet clause, with an undefined verification step, and no workstream files or tracks the unmet clause. After the close, nothing exists that would detect it staying undone. Name what "verify" checks, and either file #308's unmet clause or record it explicitly as accepted-and-dropped. | | |
| T17 | testability | MAJOR | The two front doors of workstream F and the relocation of workstream C are never tested against each other. F states that the gate imperative rides tool results verbatim so no second rendering path exists, but nothing asserts that claim: no test compares the CLI projection and the MCP tool result for the same gate. C's only live evidence came through the CLI door, so if F ships, the channel that carries C's relocated instructions is one the tracer never exercised. Add a same-gate equivalence assertion across the two doors, and state whether C's tracer must be re-run through the production MCP door. | | |
| T18 | testability | MAJOR | Ruling 3 makes workstream F's central claim permanently unfalsifiable, and the spec does not record the consequence. Skipping the bare-descriptions control arm means the 14-versus-24-to-27 call difference can never be attributed between MCP structure and the teaching sentences written into the tool descriptions — the spec already concedes part of the win came from the sentences. That matters because ruling 2 spends roughly 1,000 always-loaded tokens on schema to buy about 4,500 back: if the win is the sentences, the same sentences in CLI help buy it at near-zero schema cost, and no test in the spec compares that alternative. At minimum, make ruling 2's net always-loaded token delta a measured acceptance criterion rather than a projection. | | |
| T19 | testability | MINOR | "Falsified by a golden-output diff" is tautological when the golden file is regenerated after the change. A golden test certifies whatever the code now emits; it cannot falsify the claim that `current` is the complete state channel. Write the B goldens before the change and assert the intended diff, or replace them with the property test in T9. | | |
| T20 | testability | MINOR | Workstream A's assertion that each gauge file carries "an advancing fill" is nondeterministic. A short-lived subagent can legitimately finish without its context fill advancing between readings, so the test fails for a correct system, and a test that flakes is a test that gets disabled. Assert instead that each reading carries the agent's own model and a plausible fill, and check advancement only on an agent the test keeps busy long enough to guarantee it. | | |
| T21 | testability | MINOR | Workstream A's scan-performance risk has no budget and no named signal for when it bites. Identity resolution reads transcripts on the PostToolUse path, which runs on every tool call, so cost scales with transcript count and length on exactly the long runs where it hurts most, and degradation appears as general slowness rather than as a governor fault. "Worth revisiting only if it bites" needs something that bites audibly: record resolution time in the gauge write, and state the per-call budget above which it is a defect. | | |
| T22 | testability | MINOR | The Confirmation block asks the confirmer to record "Assumptions exercised" and "Assumptions accepted untested", but the spec never enumerates its assumptions in one place. Untested items are scattered through the exploration record, the workstream bodies, F's known unknowns, and the threshold-discipline section, and no list collects them. The block therefore cannot be filled completely or checked for completeness by anyone, including the tooling that gates confirm. Add an explicit assumptions list that the two lines partition. | | |
| T23 | testability | MINOR | The threshold-discipline claim that "placeholder grades are cheap to revise by construction, because none of them is wired into a mechanism that would resist change" is asserted, not tested, and it is false for at least workstream E, where revising the cluster boundaries after roughly a hundred issues have been closed and consolidated is not cheap, and arguably for C, where reverting means re-editing spine templates and re-running the tracers. Either scope the claim to the workstreams where it holds, or state the revert path for E and C that makes it true. | | |
