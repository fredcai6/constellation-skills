# Critic — simplicity / YAGNI lens

| ID | Lens | Severity | Finding | Disposition | Reason |
|---|---|---|---|---|---|
| F-S1 | simplicity | MAJOR | The "step-lighter" epic is an admitted-fictional wrapper. The spec says outright "the grand unifying theory is a fiction" and "each piece stands on its own merit," then bundles ~9 sections (engine answerability, launcher portability, CI, a plan-annotation schema, prototyper template edits, plan linting, dispatch doctrine, test hardening) under one epic anyway. These share no data, no ordering constraint, and no common surface — they are ~5 unrelated issues. An epic exists to coordinate work that must move together; nothing here must. Cut the wrapper and file S4 (launcher), S5 (CI), S2/S3 (answerability), and S10 (hardening) as independent issues that can land in any order. The wrapper adds admiral/wave ceremony and a false "these belong together" story for zero coordination benefit. | | |
| F-S2 | simplicity | MAJOR | S6's guess-grading schema is ceremony dressed as minimalism. It ships a formal grammar (`@grade: <tier>[ /provenance][ · leans <ids>][ · settle: <experiment>]`), a closed 3-value tier enum, a closed 3-value provenance enum, a new linter (`grade_lint.py`, does not yet exist in `scripts/`), and a 4-branch executor rule table — all to annotate plan lines. The spec's own defense that "all three candidates converged" is convergence among three variants of the same idea, not evidence the mechanism is needed. A plain prose convention ("mark guesses and name the cheapest way you'd check them") delivers ~80% of the value with zero grammar, zero enum, zero linter to maintain. The schema is a type system for annotations built before anyone has drowned for lack of one. | | |
| F-S3 | simplicity | MAJOR | S2.3 "ports-lite internals" is speculative abstraction for out-of-scope work. It directs restructuring the renderer into `state(cl) -> view dict` + `render_human(view)` today so a future `json.dumps(view)` adapter for package D is cheap — while admitting "no public --json, no consumer exists" and that D (#139 conductor inversion) is explicitly out of scope and "may never come." This is the exact YAGNI anti-pattern: pay for the seam before the consumer. Just fatten `current`'s output directly; do the state/view split if and when D actually arrives and a second render path is real. | | |
| F-S4 | simplicity | MAJOR | The smallest version that delivers ~80% is S2 + S4 + S5 (+ the real test gaps in S10a/b). Those four are the only pieces backed by the x1/x4 evidence the spec cites (8.8k-token scaffolding reads, terse REFUSED, the spine.json hand-edit, no CI, launcher portability). S6 (schema), S8 (lint), S9 (doctrine restatement), S3's lint instrument, and the S11-D record are all theory-driven — no measured pain motivates them. A cold cut ships the evidence-backed four now and defers the theory-driven rest until a real case demands them. | | |
| F-S5 | simplicity | MINOR | S6 and S8 are the same mechanism counted twice. S6.5 states plainly "the ledger is the linter … `grade_lint.py` … IS S8's batched pre-flight — ideas 7 and 29 are one mechanism." Yet they occupy two separate epic sections, inflating the "~11 items" count and implying two units of work where there is one. Fold S8 into S6 (or vice versa); the plan-conflict pre-flight is a facet of the grade linter, not an independent deliverable. | | |
| F-S6 | simplicity | MINOR | S9 (return-thin/write-fat contract) changes no behavior. The spec concedes it is "already half-practiced; this names it as the contract" and "adopting a stated convention, no shape choice." A doctrine line that codifies what agents already do is documentation, not an epic item — nobody would miss it from the batch. If kept at all, it is a one-line doctrine append, not a tracked issue. | | |
| F-S7 | simplicity | MINOR | S3's enforcement instrument is premature. The doctrine line ("consume engine state only via engine output") is cheap and fine, but S3 also commits a new curator transcript-lint to enforce it. Once S2 makes `current` answer everything the caller needs, there is no remaining reason to open the JSON — S2 dissolves the behavior the lint would police. Ship the doctrine line; do not build the lint until a post-S2 transcript actually shows someone still reading raw JSON. | | |
| F-S8 | simplicity | MINOR | The S11-D "constraints record" is content-free. Its three bullets are an aspiration ("engine should run the agents as far as the harness allows"), an open question deferred to later ("decide upfront whether engine-dispatched agents may dispatch"), and a parked candidate ("capability-escalation primitive"). It binds nothing, ships nothing, and gates nothing. This is a note that belongs in the #139 issue body, not a numbered spec section presented as a deliverable. | | |
| F-S9 | simplicity | MINOR | S2's INV-3 (recovery-totality) over-specifies. It mandates that *every* (status, mutating-verb) refusal pair yield a non-generic recovery line, enumerated exhaustively in a test — a maintenance surface the spec itself flags as a named risk. The evidence-backed pain (x1's "terse REFUSED without recovery hints") is cured by adding recovery lines at all, not by a proven-exhaustive per-pair matrix. A single good generic recovery hint ("use the engine; run `current` to see your options") plus a handful of specific ones for the common cases captures the value without the totality invariant and its enumeration test. | | |
| F-S10 | simplicity | MINOR | S7(b) "captured-to-worktree" disposition works against the prototyper's reason to exist. The prototyper skill's stated job is to "build a throwaway prototype … then dispose of it." Adding a keep-it-alive disposition reintroduces an accumulating pile of worktrees/branches that a human must later garbage-collect, plus a tracking pointer from the owning issue — the exact mess disposal exists to prevent. The default (dispose, record the finding in PROTOTYPE_RESULT) already preserves the information that mattered. Drop (b); keep (a) three-valued verdict and (c) the handoff seam. | | |
| F-S11 | simplicity | MINOR | S6.2's "settle: required on every guess (free text)" produces linter theater. A linter can enforce that the field is non-empty but cannot judge whether the named experiment is real or cheap; under a required-floor rule agents will satisfice it with "check it later" to clear the gate. A mandatory free-text field that the checker cannot evaluate buys compliance noise, not honest settling plans. Make it advisory, or drop the schema per F-S2 and let the prose convention carry it. | | |

**Overall read.** This spec is roughly two designs wearing one epic. The evidence-backed half — fatten `current` and add recovery lines (S2), resolve-at-install launcher (S4), CI on the suite that already exists (S5), and the genuinely-untested engine surfaces (S10a/b, plus the real one-line doc-drift fix S10c I confirmed against `run_skill_eval.py:12` vs the now-live `launch_agent` at line 675) — is lean, motivated by measured pain, and worth shipping largely as-is. The theory-driven half — a formal grade schema with grammar/enum/linter/executor-table (S6), its restated twin the plan-conflict lint (S8), a doctrine line that codifies existing practice (S9), an enforcement lint for a behavior S2 dissolves (S3), and a content-free constraints record (S11-D) — is machinery built ahead of the evidence, and the spec's own admission that "the grand unifying theory is a fiction" is the tell. The single most valuable simplification is to stop pretending these are one epic: ship the four evidence-backed pieces as individual issues now, and let each theory-driven piece earn its place when a real case arrives (the spec already models this correctly for Threads B and C — it just failed to apply the same discipline to package A). Sharpest single cut: delete S6's schema down to a prose convention and let S8 fall out with it.
