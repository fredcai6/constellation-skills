# X4 — How developer tools teach concepts in the flow of work

**Question:** How do real developer tools and documentation practices teach concepts *in the flow of work* (not in a course), and what patterns transfer to agents writing to one expert-but-learning architect?

**Method:** ~8 web/primary sources, cited inline. Report-only; no solution designed. Each section: mechanism, then **transfers** vs **does NOT** (scoped nulls).

---

## 1. Explanatory compiler/tooling errors (Rust `--explain`, Elm, TypeScript)

**Mechanism.** These teach the concept *at the exact moment it bites*, attached to the offending code — not in a separate manual. Rust splits the surface: the inline diagnostic points at "what" and "why" using a natural ordering and color-coded labels, while `rustc --explain E0499` opens a longer conceptual essay (the rule behind "cannot borrow as mutable more than once") only when the developer asks for it — a two-tier short/deep split. Rust's RFC 1644 explicitly set out to eliminate clutter, follow a natural order for help messages, and point at both what the error is and why it occurs ([Rust RFC 1644](https://rust-lang.github.io/rfcs/1644-default-and-expanded-rustc-errors.html); [E0499 index](https://doc.rust-lang.org/error_codes/E0499.html)). Elm's "compiler errors for humans" reframes the compiler as an *assistant, not an adversary*: it shows the relevant snippet, offers a concrete hint toward a fix, and uses a collaborative tone rather than blame ([Elm: Compiler Errors for Humans](https://elm-lang.org/news/compiler-errors-for-humans)). A subtle non-condescension point specific to Rust: the checker is sound-but-incomplete, so some rejections are analyzer limits, not the learner's misunderstanding — good teaching distinguishes "this is unsafe" from "the analyzer can't prove this is safe" rather than implying user fault ([Usability of Ownership, arXiv 2011.06171](https://arxiv.org/pdf/2011.06171)).

**Transfers:** (a) anchor the teaching to the specific artifact/decision that triggered it, not a general lecture; (b) two-tier disclosure — a terse "what + why" inline, with the conceptual deep-dive available on demand (`--explain`), which is exactly the milestone-explainer / register-dial shape; (c) collaborative tone that names the *concept* and points forward to a fix; (d) separate "this is a real constraint" from "this is a limitation of the tool/analysis," so the reader isn't blamed for tool incompleteness. **Does NOT transfer:** compiler errors assume the reader is *stuck and blocked* — they're remediation for failure. An expert-but-learning architect reading a healthy build milestone is *not* in an error state, so the corrective/apologetic framing ("here's what went wrong, here's the fix") is a mismatch; the register should be "here's the concept this milestone rests on," not "here's your mistake."

## 2. Diátaxis — the EXPLANATION quadrant vs REFERENCE

**Mechanism.** Diátaxis separates four documentation modes by user need; the **explanation** quadrant is understanding-oriented and read *away from the work, in reflection*, whereas **reference** is information-oriented and consulted *during* active work like a dictionary ([Diátaxis: Explanation](https://diataxis.fr/explanation/)). What distinguishes good explanation: it (1) **makes connections** — links ideas into a web of understanding; (2) **gives the "why"** behind design decisions and constraints; (3) **discusses alternatives, counter-examples, and multiple approaches**; (4) **admits perspective** — openly reasons from a viewpoint rather than posing as neutral fact; and (5) **stays bounded** — resists absorbing step-by-step or API-listing content that belongs in other quadrants. The framework's analogy is *On Food and Cooking*: a book that changes how a cook thinks by explaining *why*, without giving recipes ([Diátaxis: Explanation](https://diataxis.fr/explanation/); [diataxis.fr](https://diataxis.fr/)).

**Transfers:** this is almost a direct spec for a build-milestone explainer (K9). Borrow: lead with the *why* and the connective tissue ("this milestone matters because it sits between X and Y"), permit discussing the road not taken, and explicitly own the perspective ("we chose this because…"). Crucially, **explanation is not reference** — don't dump the API/field listing; teach the idea. And the "read in reflection, not mid-task" framing supports making it *skippable* by an expert who just wants the reference facts. **Does NOT transfer:** Diátaxis assumes you can physically segregate the four modes into four different documents/pages. An in-flow agent message to one architect can't ship four separate docs — it must *blend* a little explanation into what is otherwise a status/reference stream, which is precisely the boundary Diátaxis warns against crossing. So the framework tells you what good explanation *looks like* but not how to *interleave* one paragraph of it into a working channel without polluting the reference; that interleaving problem is ours to solve.

## 3. Architecture Decision Records & literate programming

**Mechanism.** An ADR captures a single decision with its **context** (the problem and trade-offs faced), the **decision**, the **rationale** (why this over alternatives), and the **consequences**, kept to ~one page and stored beside the code ([Martin Fowler: ADR](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html); [adr.github.io](https://adr.github.io/)). Nygard's founding framing is the teaching motive: a newcomer facing a past decision otherwise has only "two choices: blindly accept the decision or blindly change it" — the record exists so the *why* survives the people who held it in their heads ([Fowler/Nygard](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html)). Legibility-over-time is preserved by **immutability**: accepted ADRs are never edited, only superseded by a new record, producing "a clear log of decisions and how long they governed the work." Literate programming shares the DNA — narrating the *why* inline with the code so intent travels with the artifact.

**Transfers:** the four-part skeleton (context → decision → why-not-alternatives → consequences) is a compact, non-condescending teaching unit that an agent can borrow to narrate a *choice* it made; recording the road-not-taken and the consequence is what makes it teach rather than merely announce. The immutability/supersession model also transfers: a "why" that's dated and append-only stays trustworthy, versus edited-in-place notes that rot. **Does NOT transfer:** ADRs are *durable, indexed, look-up-later* artifacts written for an unknown future reader who is presumed *not* present. An in-flow explainer to one known, expert architect who *is* present is the opposite: it can assume shared context, must be short, and shouldn't re-explain what this specific reader already decided. Writing full ADR ceremony into every in-flow message would be over-heavy and would re-teach the reader their own decisions — the durable-artifact instinct is a mismatch for the live, single-reader channel.

## 4. "Explain this code / change" in IDEs & AI assistants

**Mechanism.** These features are **pull, not push** — invoked deliberately via `/explain` or a context menu on a selected span; the tool explains only what the developer *pointed at* ([GitHub Docs: Copilot features](https://docs.github.com/en/copilot/get-started/features); [GitHub Blog: essential features](https://github.blog/ai-and-ml/github-copilot/github-for-beginners-essential-features-of-github-copilot/)). They pitch the *level* primarily via **explicit self-declared audience**: "explain this to me like I'm a Python developer" makes the assistant calibrate register to the reader's stated background and bridge from the familiar to the unfamiliar, rather than auto-detecting expertise from the code ([GitHub Docs: explore a codebase](https://docs.github.com/en/copilot/tutorials/explore-a-codebase); [DEV: Understand your code with Copilot](https://dev.to/github/understand-your-code-using-github-copilot-5375)). The useful anchor is *what the reader already knows*: explanation is framed as a translation from a known domain to the new concept.

**Transfers:** (a) **explanation is opt-in / on-demand** — the strongest signal that pitch-level should default to *quiet*, expanding only when asked, which validates a register dial the architect controls; (b) calibrate to *declared* expertise and bridge from what the reader already knows rather than guessing; (c) explain the *selected thing*, tightly scoped, not the whole system. **Does NOT transfer:** Copilot leans on the *human* to declare their level each time ("like a Python dev") — it offloads calibration to an explicit prompt. An agent writing proactively to a fixed, known architect can't demand a re-declaration every message; it must *hold a persistent model* of this one reader's level (a standing register setting), which the IDE feature never has to do. So the "let the user state their level" mechanism doesn't map cleanly onto a proactive, single-persistent-reader channel.

## 5. Progressive disclosure / glossary-on-hover

**Mechanism.** Progressive disclosure moves complex or infrequent detail out of the primary view into a secondary layer revealed on demand, reducing cognitive load while keeping the expert's default view clean ([UXPin: Progressive Disclosure](https://www.uxpin.com/studio/blog/what-is-progressive-disclosure/); [IxDF: Progressive Disclosure](https://ixdf.org/literature/topics/progressive-disclosure)). Glossary-on-hover is the fine-grained case: a definition surfaces in a tooltip only when the reader hovers an unfamiliar term, giving "answers without leaving the current task while keeping interfaces clean." Microsoft's guidance is nearly a spec for gloss-on-first-use: *define terms at first use*, and when the extra info is a short descriptive fragment, put it in a tooltip/infotip so the term is introduced "without overwhelming the interface" ([Microsoft: Progressive Disclosure Controls](https://learn.microsoft.com/en-us/windows/win32/uxguide/ctrl-progressive-disclosure-controls); [Mobbin: Tooltip UI](https://mobbin.com/glossary/tooltip)).

**Transfers:** this is the cleanest map to gloss-on-first-use + register dial. Borrow: (a) the *default expert view stays uncluttered* — the definition is present but latent, costing the expert nothing; (b) **define on first use, then don't repeat** — introduce a term once, glossed, and thereafter use it bare; (c) keep the gloss to a short descriptive fragment, not a lecture; (d) reveal-on-demand so the reader pulls depth only when wanted. **Does NOT transfer:** hover glossaries depend on a *rich interactive medium* — a real hover/click target, a layer that's spatially separate from the main text. A linear agent message (plain text / markdown, read top-to-bottom, possibly on mobile) has no true "hover layer": there's no way to make the gloss occupy zero space until wanted; any inline parenthetical still consumes reading attention for the expert. So the *intent* (latent, on-demand, non-cluttering) transfers, but the *interaction affordance* that makes it free does not — in a linear channel a gloss is never truly zero-cost, which forces a real judgment call about when to spend the words.

---

## Cross-cutting takeaways for the designer

- **Two-tier / short-then-deep is universal** (Rust inline vs `--explain`; tooltip vs full doc; Diátaxis reference vs explanation). The in-flow default is *terse*; depth is *pulled*. Strongest single pattern for K9 + the dial.
- **Anchor teaching to the triggering artifact** (compiler errors, /explain-the-selection, ADR-per-decision) — teach the concept *this milestone/decision* rests on, not general theory.
- **Own the perspective and name alternatives** (Diátaxis, ADRs) — this is what makes explanation teach without sounding like neutered reference or a lecture.
- **The consistent null:** every borrowed tool assumes either a *blocked/erroring reader* (compilers), a *future absent reader* (ADRs), a *re-declaring human* (Copilot), or a *rich hover medium* (glossaries). Our case — a proactive agent, a live, known, expert-but-learning single reader, a linear text channel, a persistent register — matches none exactly. The **mechanisms transfer; the calibration-and-interleaving problem is ours**: holding a standing model of one reader and blending one paragraph of explanation into a working stream without either condescending or cluttering.
