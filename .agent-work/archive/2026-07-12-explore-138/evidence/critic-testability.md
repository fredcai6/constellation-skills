| TS1 | testability | BLOCKING | The check-FAILURE decision point is not derivable from `items` state, so its rail string cannot be deterministically emitted OR unit-tested. D2 asserts all five decision-point types "derive from existing `items` state" and are "unit-testable by substring from constructed spine states." But a check failure is a refusal: in `checklist_engine.py` `advance`/`start` raise `EngineError` (e.g. "postconditions unmet") which is caught in `main()` (lines 1411-1416) and printed to **stderr** — a different code path from the `current`/`advance`/`start` return values the rail rides. After a failed `advance` the gate is still `in-progress`, so the spine state is IDENTICAL to plain mid-flight and to a lease-refusal or ordering-refusal. `_rail` keyed on `items` state therefore cannot tell "a check just failed" from "you are mid-flight" or "your lease is stale," and no constructed spine state uniquely means "a check just failed." The longest, most load-bearing rail string (scoped-nulls, the two forbidden exits) is precisely the one that cannot be reliably triggered or falsified. | | |
| TS2 | testability | MAJOR | The mid-flight -> near-terminal boundary is undefined, so the state->type mapping the D2 unit tests assert against has no decidable cutover. The mid-flight string says "you are N steps from done" and near-terminal is a distinct string, but no N threshold is given for when a state stops being mid-flight and becomes near-terminal. A "substring per decision-point type from constructed spine states" test cannot be written without inventing the threshold the spec omits; two reviewers would test different cutovers. | | |
| TS3 | testability | MAJOR | The design's stated purpose is durability against wording being stripped (Intent: #101 found protective force "stripped from nine other skills into pointers that don't fire"), but no D6 arm measures durability — every arm measures one-shot strict terminal completion on a fresh snapshot. Corpus-only (D1 wording) can hit target today; the kill condition would then shrink the engine channels using a metric that structurally favors the very wording proven non-durable. The core premise (engine-delivered doctrine survives where wording erodes) is therefore unfalsifiable by the measurement plan — the thing the design is FOR is not what any arm tests. | | |
| TS4 | testability | MAJOR | Arm nesting confounds each channel's contribution with layering order, so "each arm's contribution visible" (Intent, D6) is overclaimed. The rail (D2) restates the same four-clause doctrine D1 already stamps into skill text, and D1 is present in ALL three arms. "+rail adds nothing over corpus-only" cannot distinguish "redundant with the D1 wording already injected" from "ineffective in isolation." The removal-candidate logic ("any channel whose arm adds nothing measurable is a removal candidate") can therefore drop a channel (rail or hooks) that would be sufficient on its own, because no arm exercises rail-without-corpus-wording. | | |
| TS5 | testability | MAJOR | The falsification conditions are point comparisons whose decidability is deferred out of the spec. "Falsified if +rail arm <= corpus-only arm" (Testing pathways) has no preregistered run count (punted to #136) and no noise margin, while x3 records 8-10pt swings from formatting alone. With small N and that noise floor, a genuinely-helpful rail below the noise floor is falsely "falsified" and a useless one falsely "kept." The kill condition inherits this indecidability: it fires on an undefined "adds nothing measurable." | | |
| TS6 | testability | MAJOR | The +rail+hooks arm bundles a live-testable hook (Stop) with a component the spec itself says is not exercisable on demand (SessionStart source=compact re-injection; Testing pathways: "not currently constructible on demand"). A passing +hooks arm cannot show whether the compaction re-injection channel does anything, because the eval never forces a compaction. The compaction channel rides untested inside an arm labeled "measured," and its contribution is silently attributed to the hook suite as a whole. | | |
| TS7 | testability | MINOR | The Stop-hook escape hatch has no end-to-end scenario in the harness. D3's falsification "Stop-hook refusals trap a stuck agent (escape hatch fails)" requires a run that makes no journal progress across three consecutive Stop events, but the measured arms run the normal eval task, which is not a stuck-agent scenario. Only the unit decision-logic (stdin JSON -> allow/refuse/nudge) is decidable; the real trap-avoidance behavior — the safety property the 3-strike counter exists to guarantee — is unfalsified by the plan. | | |
| TS8 | testability | MINOR | Two asserted invariants have no machine-decidable test. Neither "flat" nor "warm" is decidable by substring or any stated check, so nothing catches a warm/enthusiastic phrase leaking into a rail or gate string during implementation or later edits. The single-source claim controls WHERE the strings live, not their register. | | |
