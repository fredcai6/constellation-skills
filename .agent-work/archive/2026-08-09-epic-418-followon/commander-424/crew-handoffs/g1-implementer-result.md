## Tool-grouping decision (the judgment call the handoff asked me to own)

**7 tools, 13 of 18 verbs covered:**

| Tool | Verbs (action enum where >1) |
|---|---|
| `spine_status` | `current` (read-only) |
| `spine_lease` | `claim` \| `release` \| `heartbeat` |
| `spine_start` | `start` |
| `spine_advance` | `advance` |
| `spine_evidence` | `attest` \| `attach` \| `waive` |
| `spine_halt` | `block` \| `resume` |
| `spine_survey_result` | `record` \| `consolidate` (survey plans only) |

**Uncovered (CLI-fallback table, in the server's module docstring):** `skip`, `reopen`, `append`, `amend`, `flag-candidate`.

**Reasoning.** The handoff was explicit that the prototype's uncovered set (`heartbeat, skip, reopen, append, amend, waive, attach, flag-candidate`) was wrong because `attach` and `waive` are load-bearing — a door missing `attach` cannot satisfy a `user-decision` checkpoint, and a door missing `waive` cannot close a gate whose check the principal accepted as non-blocking. I folded `attest`, `attach`, and `waive` into one `spine_evidence` tool (all three are "apply evidence to a condition" actions with different argument shapes, not different concerns) — this covers both load-bearing verbs **without** adding a tool slot, keeping the count at 7 while fixing exactly the defect the handoff named. `heartbeat` rides free inside `spine_lease` for the same reason (cheap to add, no new slot).

The 5 I left uncovered are the ones that are genuinely rare on the drive loop, not merely "the leftover count to hit 18 minus 13": `skip`/`amend`/`append` are deliberate re-planning decisions (a human/commander move, not a step the agent driving the plan reaches for); `reopen` is a high-blast-radius rework cascade the CLI's explicit invocation shape is a safer gate for than a one-line tool call; `flag-candidate` is infrequent (once-per-run at most) and costs nothing extra at the CLI right when it comes up. I did not evaluate `reopen` as carefully as `attach`/`waive` — see Workflow Feedback.

- **Context rediscovered:** the exact CLI flag shape for every one of the 18 verbs (`--cond`/`--which`/`--evidence` for `attest`, `--force`/`--reason` for `waive`, `--field K=V` for `attach`, etc.) had to be read directly out of `checklist_engine.py`'s `parse_args()` — there is no single reference table for this (the closest is `checklist-engine.md`'s verb-loop prose, which names the verbs but not their exact argparse shape). Since this gate's entire job is building a typed wrapper around exactly that argument surface, a maintained flag-shape table (even just `parse_args()`'s own docstring-adjacent comment block) would directly serve the next person building a second front door.

- **Instructions improvised around:** none in the skill or engine doctrine itself. One real bug, entirely of my own making, cost real time: `tests/test_mcp_spine_server.py`'s original `test_generated_config_server_actually_answers_a_real_tool_call` used `self.assertTrue(line, f"no reply; stderr={proc.stderr.read()}")` — Python evaluates that f-string **unconditionally**, so even on the success path it called the blocking `proc.stderr.read()` on a still-open pipe with no EOF, and the whole suite hung indefinitely. It reproduced under `pytest` and `python -m unittest` identically but NOT in a bare script — the difference was never pytest/environment (I spent real effort ruling out env-inheritance, capture mode, and interpreter identity before finding it), it was this single line. Found by `faulthandler.dump_traceback_later(6, exit=True, ...)` pinpointing the exact blocked frame; fixed by moving the stderr read inside an explicit `if not line:` branch. This is genuinely worth a workbench-level testing note (see triage candidate 3 above) since it is not specific to this task — any subprocess-pipe assertion with a "helpful" f-string message is one keystroke from the same deadlock.

- **What would have made this easier:** a one-line convention note in `global-crew.md` or `checklist-engine.md` — "when asserting on subprocess pipe I/O, never put a blocking read inside an eager assertion message" — would have saved the ~20 minutes spent proving the hang wasn't an environment/pytest artifact before it was a code bug. Otherwise: nothing. The handoff's pre-settled delivery-path decision (do not re-litigate .mcp.json vs per-dispatch config) and its explicit prototype pointer both paid for themselves directly — I did not have to discover either from scratch.
