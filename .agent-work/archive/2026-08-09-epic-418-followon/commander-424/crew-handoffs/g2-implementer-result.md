## Workflow Feedback

- **Handoff gaps:** the handoff's rule 1 says "mutate one imperative, watch the property go red"
  as if that is a single, obvious move. It is not, for a property whose two arms share one spine
  file by design (my own architecture choice, but a natural one given the DC3 house pattern) —
  mutating the *source template* cannot diverge the two arms, only mutating what one arm *reads*
  relative to the other can. I discovered this empirically (ran the literal instruction, got an
  honest green, had to reason out why). A future handoff for this shape of property test would
  save real time by naming explicitly: "the red-state mutation must land on one arm's input only —
  identify where the two arms' inputs are shared before designing the demonstration."
- **Context rediscovered:** `scripts/code_map/discovery.py` uses `git ls-files`, so a new,
  unstaged test file is invisible to a map rebuild — not documented in the handoff or in
  `checklist-engine.md`'s map-freshness note ("rebuild with `python -m scripts.code_map build
  --root .` and commit, or the suite goes red"), which reads as if rebuild-then-add is the right
  order. It is not, for a brand-new file: stage first, then rebuild, then commit. Cost one extra
  rebuild-and-recheck cycle here; would be worth a one-line addendum in that doctrine file.
- **Instructions improvised around:** the handoff and my own plan's `m4-live-red-demo` imperative
  both assumed mutating a real shipped template file would produce red. When it didn't (see the
  Evidence section's negative result), I treated `m4`'s check:null postcondition as license to
  attest a corrected, more rigorous demonstration instead — the engine's `amend` verb would have
  let me formally retext the imperative, but since the postcondition itself was already
  attest-only, I judged a full explanation in the attest note (plus this section) to be the
  closest compliant response rather than invoking `amend` for a wording-only correction.
  Separately: an attempted temporary Edit to `scripts/mcp_spine_server.py`, meant purely to prove
  the door's own wrapper could be caught misbehaving (then immediately restored, mirroring
  `DC3PositiveControlTests`'s technique against a real component), was refused by the harness's
  permission classifier. I treated that refusal as authoritative rather than working around it,
  and redesigned the demonstration to touch no tracked file — see the Evidence section.
- **What would have made this easier:** knowing up front (from the handoff or from
  `test_mcp_identity.py`'s docstring) that `mcp_spine_server.py` is fenced against even a
  temporary, restored edit — not just a permanent one — would have saved the one wasted Edit
  attempt and let the scratch-script design start immediately.
