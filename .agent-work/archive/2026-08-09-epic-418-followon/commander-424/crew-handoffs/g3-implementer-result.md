## DC3 verdict: does an in-session subagent share its parent's server?

> Does an in-session Task-tool subagent share its parent's already-launched MCP server?

**YES, measured.**

**What was measured, exactly:** a real, live headless dispatch —
`claude -p "<prompt>" --mcp-config <generated>.json --strict-mcp-config --allowedTools "mcp__spine__spine_status Task"`
(Claude Code 2.1.226, this host) — against a scratch spine whose gate imperative carried an
unguessable per-run nonce. The prompt instructed the top-level agent to (1) call `spine_status`
itself, then (2) use its own `Task` tool to dispatch exactly one subagent whose sole instruction was
to attempt the identical `spine_status` call and report the verbatim result (or `SUBAGENT_NO_TOOL` /
`SUBAGENT_ERROR:` if it could not). `--strict-mcp-config` means the ENTIRE session — top-level agent
and anything it dispatches — has exactly one MCP server available, the one generated for this one
dispatch; nothing else could have supplied an answer.

**Result, reproduced twice with independent nonces:**

```
$ D=.agent-work/epic-418-followon/commander-424/crew-plans/scratch-g3-live
$ timeout 280 claude -p "$PROMPT" --mcp-config "$D/config.json" --strict-mcp-config \
    --allowedTools "mcp__spine__spine_status Task" --permission-mode acceptEdits \
    --output-format json > "$D/dispatch_stdout.json" 2> "$D/dispatch_stderr.txt"
EXIT: 0
```
Run 1 result (`is_error: False`):
```
TOP_LEVEL_RESULT: ... ACTIVE g1 [pending] — TASKTOOL-PROBE-NONCE::Tcfbc3ec6f9c5d8b0 ...
SUBAGENT_RESULT: SUBAGENT_TOOL_RESULT: ... ACTIVE g1 [pending] — TASKTOOL-PROBE-NONCE::Tcfbc3ec6f9c5d8b0 ...
```
Run 2, fresh nonce, fresh spine, cleared call log (`is_error: False`):
```
TOP_LEVEL_RESULT: ... ACTIVE g1 [pending] — TASKTOOL-PROBE-NONCE::T2-de42804b5a4dcafc ...
SUBAGENT_RESULT: SUBAGENT_TOOL_RESULT: ... ACTIVE g1 [pending] — TASKTOOL-PROBE-NONCE::T2-de42804b5a4dcafc ...
```

Both the top-level agent's own call and the Task-tool subagent's call returned the SAME unguessable
nonce, in both independent runs — a model cannot invent a random 16-hex-char string, so its presence
in the subagent's own reported result proves the subagent genuinely reached the real engine, not a
fabricated echo. Corroborated independently of the model's self-report, from the server's own
ground truth: `mcp_calls.jsonl` shows **exactly 2** `"verb": "current"` entries per run — matching
"top-level call once + subagent call once," no more, no less (evidence:
`crew-plans/scratch-g3-live/{spine.json,config.json,dispatch_stdout.json,dispatch2_stdout.json,mcp_calls.jsonl,nonce.txt,nonce2.txt}`).

**Scope of the YES, stated precisely, so it is not over-read:** this measures that a Task-tool
subagent inherits the SAME MCP configuration/server access as its dispatching `claude -p` process
when that process used `--strict-mcp-config`. It does not, and cannot from outside the harness,
distinguish "the subagent reused the literal same OS-level server connection object" from "the
subagent independently resolved the identical `--strict-mcp-config` file and got its own new server
process bound to the identical `SPINE_FILE`/`SPINE_SESSION`" — but per the handoff's own scoping
("DC3 is about the door: whether a subagent... can reach the *parent's server instance*, and through
it the parent's lease and reading"), both of those are the SAME answer to the question that actually
matters: the subagent reached the parent's identity with no configuration of its own. Scoped to
Claude Code 2.1.226, this host, one server/one tool named in `--allowedTools`, print-mode with
`--output-format json`, one level of Task-tool nesting. Not tested: other CLI versions, multiple
concurrent subagents, or a subagent given a *narrower* `allowedTools`/subagent-type restriction than
its parent.

**Why this matters, and why it does not contradict the committed suite's own "NO leak" finding:**
the committed `DC3InheritanceMechanismTests` measures a DIFFERENT, narrower case — a subagent
launched as a genuinely FRESH OS process inheriting a plain, unconfigured environment, with no
`--mcp-config` of ANY kind in play. That case correctly shows no identity. This live experiment shows
the case the STATE_NOTE's question is actually pointed at: a Task-tool subagent dispatched FROM
INSIDE an already-`--strict-mcp-config`-scoped session inherits that scope wholesale. Both are true,
about different scenarios, and the distinction is exactly the "per-dispatch (top-level process) scoping,
not per-agent-turn scoping" finding recorded as a triage candidate above — it is new information the
MISSION_FRAME did not have, not a contradiction of anything measured there.

This means per-dispatch identity scoping (`gen_mcp_config.py`) is per TOP-LEVEL PROCESS, not per individual agent-turn within that process — if a workflow ever wants a Commander's own Task-tool-dispatched crews to carry genuinely different spine identities than the Commander itself or than each other, this finding shows that is NOT automatic and would need its own design (e.g., each crew dispatch would need to be its own separate `claude -p` invocation with its own `--mcp-config`, which is exactly the existing crew-dispatch pattern in this repo — worth Commander/Cartographer confirming that assumption is intact given this new evidence, rather than assumed).
3. **The two-spines-share-a-session-id observation named in MISSION_FRAME (`86708414-f5d3-40d3-8c9a-2f96d1ccdc14`) is real and reproduces trivially: every Task-tool-dispatched crew in this Commander's run (Commander itself, g1-implementer, g1-reviewer, this g3-implementer) shares one Claude session id, visible directly in this run's own scratchpad path.** Per the handoff's own instruction this is NOT DC3 and I have not treated it as such or touched engine lease semantics to "fix" it — flagged here only so it is on record as confirmed-real, not hypothetical, for whoever eventually scopes the engine-side fix.
