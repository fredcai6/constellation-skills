Packet: src/data — Data Collection and Storage

status: currentlevel: containersrc/data/confidence: highstruct:data

Detail (from the Cartographer packet)

Responsibility

Sole write path to the SQLite database. Loads F1 session data from FastF1, extracts features, and persists results. Owns the database schema, query interface, and all DB operations.

Analysis code in other packages reads from the DB; it does not call FastF1 directly.

Current coupling note: collector.py imports evo domain structures through src.evo_predictor.compound_adapter and src.evo_predictor.models to persist compound allocation data. This is current code truth, not a preferred new dependency direction.

Key Modules

collector.py — F1DataCollector Entry point for data ingestion. collect_season(year) → collect_race(year, gp_name) → collect_session(year, gp_name, session_type). Handles retry logic with exponential backoff, rate limiting (INTER_SESSION_DELAY=55s), and rate-limit detection on "500 calls/h" errors (RATE_LIMIT_WAIT=1200s). Extracts session_classifications for FP1/FP2/FP3/Q/R into a dedicated DB table. FP position derivation uses best-lap ordering because FastF1 FP results have Position=NaN.

database/ — DatabaseManager (package) All SQLite operations. DatabaseManager is assembled in database/manager.py from mixins split across _core.py, _ingest.py, _metadata.py, _results.py, and _telemetry_store.py; it is re-exported from database/__init__.py so from src.data.database import DatabaseManager is unchanged. _metadata.py itself is now a thin combiner (issue #302): DatabaseMetadataMixin inherits DatabaseCircuitMetadataMixin (_metadata_circuit.py — circuit info, weekend entry list, race start order) and DatabaseSessionMetadataMixin (_metadata_session.py — session classification, race points, completeness/row-count queries). Schema (schema.sql + _core.py, 14 tables): core session data (sessions, lap_times, telemetry, weather); classifications & grid (session_classifications, race_start_order, weekend_entry_list); dense weather, backfilled out of band (session_gap_weather, session_surface_features — see weather_features.py); derived per-session fuel-burn (session_fuel_features — #575 g4, written by physics fuel_features.populate_fuel_features_for_db, see below); circuit & terrain geometry (circuit_info, session_terrain_profile_meta, session_terrain_profile_samples); physics state persistence (processed_telemetry). _core.py extracts two idempotent create-or-migrate helpers — _ensure_session_surface_features (create + additive ALTER TABLE ADD COLUMN for the #575 g2 wet columns wet_lap_count/total_lap_count/wet_lap_fraction on pre-existing DBs) and _ensure_session_fuel_features — both called from _apply_schema_upgrades so the migration path and schema.sql stay in lock-step. Upsert-safe writes via upsert_session_classification. Read methods: get_session_classification, get_session_driver_info, get_race_points, has_session_classification, get_quali_best_valid_laps_batch. Completeness/row-count metadata lives in _metadata_session.py (get_collection_row_counts, which deliberately excludes dense weather). Raises DatabaseError on failure. Uses connection timeouts and transaction handling.

get_quali_best_valid_laps_batch(year, round_nums) → {round_num: {driver_id: best_lap_seconds}} (_metadata_session.py): batched Q-session best-lap query; filters valid_lap=1, no pit laps, lap_time NOT NULL; groups by round and driver. Returns empty dict for all rounds with no matching rows. Consumed by src/evo_predictor/quali_pace_gap_history.py for the pace-gap form encoding.

_telemetry_store.py — DatabaseTelemetryStoreMixin Persistence for physics/preprocessing outputs. processed_telemetry table (per-point Kalman-RTS state: px/py/pz, vx/vy/vz, ax/ay/az + per-channel sigma_*, innovation_pos/speed, source_flags) via insert_processed_telemetry / get_processed_telemetry / delete_processed_telemetry. Pipeline-tighten Task 10 (2026-07-06): gains eight PVAT velocity-frame columns — s_m (cumulative arc length), v_ms (speed), a_long_ms2/a_lat_ms2 (tangential/normal acceleration projections), sigma_v/sigma_a_long/sigma_a_lat/cov_v_along (delta-method uncertainty) — written by insert_processed_telemetry's extended column list; _core.py's new _ensure_processed_telemetry(conn) additively ALTER TABLEs these eight columns onto a pre-existing table (no-op on a fresh DB, whose executescript(schema.sql) already creates them; no-op when already present), called from _apply_schema_upgrades alongside the existing surface-features/fuel-features migration helpers. Terrain geometry (session_terrain_profile_meta + session_terrain_profile_samples: per-station distance_m/altitude_m/grade/theta_rad + optional bank) via upsert_session_terrain_profile / get_session_terrain_profile, with full input validation (distance_m strictly increasing, finite arrays, bank-availability mask).

processed_telemetry now has a real producer (LIVE, pipeline-tighten Task 10). src/physics/ideal_lap/pvat_writer.write_lap_pvat persists a fitted lap's smoother output (position/velocity/acceleration state + the PVAT velocity-frame channel above) to this table — a physics-region writer, not preprocessing (see packets/preprocessing.md's DB-only boundary note for why). It is reached opt-in through physics/layer2/session_race.load_race_stints's pvat_db parameter (None everywhere by default — zero rows written) and exercised by scripts/export_pvat.py, the one caller that turns it on. Still no consumer: nothing in src/ reads processed_telemetry back — the live preprocessing→physics fit path still re-runs the smoother from raw streams per consumer, passing processed_telemetry as an in-memory DataFrame from preprocessing/trajectory/physics_adapter.smoother_to_processed_telemetry, not this table. The terrain tables are still written only by scripts/probe_terrain_profile.py. Whether to build a consumer that reads the persisted PVAT channel back (retiring the in-memory re-smoothing) remains an open design question — see the updated open question in index.md and packets/physics.md's Open Questions.

load_fastf1.py — FastF1Loader FastF1 session loading and feature extraction. Provides extract_practice_features(), extract_race_features(). Clean-lap filtering excludes pit laps and invalid laps. Used only by the collector; not imported by analysis code.

query_builder.py — QueryBuilder Dynamic SQL construction with parameter binding. Supports SELECT, INSERT, UPDATE, DELETE, COUNT; handles NULL, IN clauses, and empty lists. Eliminates SQL duplication across DB methods.

weather_features.py Derives the two dense weather feature tables from session weather and lap data plus the Open-Meteo archive API:

  • session_gap_weather — rain-between-sessions (gap_rain_flag, gap_precip_mm, gap_hours) via collect_gap_rain_for_event().
  • session_surface_features — dry-running counts since the last wet/reset event (dry_lap_count_since_reset, log_dry_lap_count_since_reset) via derive_surface_features_for_event(), plus (#575 g2) a graded per-session wet-race flag in the wet_lap_count/total_lap_count/wet_lap_fraction columns via session_wet_lap_features(db, session_id) — a DB-only WET/INTERMEDIATE lap_times.compound fraction (same criterion as _session_rain_flag; no FastF1/Open-Meteo call), driven across a season by populate_wet_features_for_db(db_path). These wet columns are written through the non-clobbering upsert_session_wet_features (_ingest.py) — an INSERT ... ON CONFLICT(session_id) DO UPDATE of only the three wet columns, deliberately NOT the whole-row INSERT OR REPLACE upsert_session_surface_feature, so it never touches session_rain_flag/dry_laps_*/gap_rain_flag/feature_status owned by the heavy derive_surface_features_for_event pipeline. Populated 2019-2026. Consumed read-only by physics (burn_rate_calibration.session_wet_fraction) to exclude wet races from the dry fuel-burn baseline. CLI: scripts/populate_wet_features.py (non-map node).

The derived session_fuel_features table (#575 g4) is populated from the physics region (src/physics/fuel_features.py), not weather_features.py; the data region owns only the schema + accessors (upsert_session_fuel_features/get_session_fuel_features in _ingest.py, table create in _core.py).

Both dense-weather tables are optional and backfilled out of band. Every row carries a feature_status (ok, missing_previous_session, missing_session_times, missing_location, external_weather_unavailable, unknown_gap_weather) so consumers can tell a real value from an unavailable one. Rows may be absent entirely for sessions that have not been backfilled.

protocols.py Data access protocols (structural typing for DB interfaces).

telemetry_store.py — TelemetryStore (#494) Standalone SQLite store (separate from database/) for the raw per-driver flying-lap telemetry windows the physics fit pipeline consumes. Persists position (X/Y/Z decimetres), car streams (Speed/Throttle/Brake/Gear/DRS), per-lap metadata, and session weather at per-flying-stint granularity — the minimal superset that reproduces the fit chain (smoother calibration needs the whole fast-lap stint). Units stored as FastF1 provides them so loaders.driver_streams unit conversions reproduce identically. DB-first source for session_fit.load_quali_session; cache-fallback when absent. Regenerable from cache via scripts/backfill_telemetry_store.py (git-ignored like other derived stores). Default path: data/telemetry_store.db.

telemetry_session.py — DBSession (#494) FastF1-session-shaped shim over a TelemetryStore payload. Reconstructs the fixed surface session_fit.load_quali_session consumes (car_data, pos_data, laps.pick_drivers, get_driver, drivers, weather_data) from the durable DB instead of the FastF1 cache. Time columns rebuilt as pandas Timedelta (FastF1's native dtype); X/Y/Z (dm) + Speed (km/h) returned raw so loaders.driver_streams conversions apply identically.

Data Flow

FastF1 API
  → load_fastf1.py (session loading)
  → collector.py (retry, rate-limit, extraction)
  → database/ (upsert via DatabaseManager)
  → data/f1_data_*.db (SQLite canonical store)

External Dependencies

  • fastf1 library — session data source
  • pandas — lap data, weather data
  • SQLite (stdlib sqlite3)
  • src/evo_predictor - compound allocation domain model and adapter used during ingestion

Known Limits

  • Collection script (scripts/collect_evo_data.py) is external to this package; it drives F1DataCollector.
  • FP position derivation is a workaround for FastF1 returning NaN positions in free practice.
  • Rate-limit detection is heuristic string matching on error messages.

Dense weather availability (issue #201)

Dense weather (session_gap_weather, session_surface_features) is backfilled out of band and is not required for a session to be considered complete. The current model/strategy pipeline must not fail when dense rows are missing, and validation treats their absence as a low-priority, warning-only gap:

  • scripts/check_data_quality.py reports missing dense weather as missing_dense_weather at low priority and never as a failure. It summarizes coverage by season/session in the report's "Season/session coverage" table (weather_rows and dense_weather_rows columns).
  • DatabaseManager.get_collection_row_counts() (src/data/database/_metadata_session.py) deliberately excludes dense weather from the completeness row counts.
  • scripts/collect_evo_data.py emits a warning (not a failure) when weather rows are missing.

Rule for weather-aware features: any new feature that reads dense weather must check availability before trusting it — prefer the per-row feature_status (ok means usable) over assuming a row exists or is populated. Do not assume dense rows are complete; treat missing/!= "ok" rows as "unknown" and fall back gracefully.

Flag consistency is enforced by the data-quality report, which flags both has_weather=1 with zero weather rows and weather rows present with has_weather false/missing.
