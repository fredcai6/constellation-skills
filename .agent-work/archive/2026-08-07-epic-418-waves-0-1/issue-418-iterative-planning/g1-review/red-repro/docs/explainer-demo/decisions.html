Fuel Burn-Rate Calibration Design

decision:burn_rate_calibration_design · `current` · `2026-07-02` · `user decision`
Governs: struct:physics struct:physics.layer2 struct:data

Question

How should a per-race fuel burn rate be measured and delivered to the physics race-stint mass model, given that (a) the existing mass_model.py must stay pure and DB-free, (b) a calibration must not become a fitted/tunable knob that drifts, and (c) rain-affected races contaminate any burn baseline?

Decision

The burn rate is a regulation-anchored, zero-fit, per-(season, circuit) estimate, DB-stored in a derived table and injected into the mass model through an optional override seam; wet races are excluded from the baseline.

  • Regulation-anchored, zero-fit. burn_rate_calibration.per_lap_burn_kg = flow_rate_cap_kg_per_s * mean_throttle_fraction * lap_duration_s, where the flow cap is a literal cited FIA constant from FUEL_REGULATIONS (100 kg/h flat 2014-2025; energy-based ~70 kg/h-equivalent from 2026). Nothing is fitted — the only measured input is the throttle integral from telemetry.
  • Per-(season, circuit), no pooling. season_burn_rate_estimate(year, gp) aggregates clean-lap estimates for one race; there is no cross-season or cross-circuit pooling.
  • DB-stored + injected via the mass_model override seam. The calibrated rate is written to the derived session_fuel_features table (data region) by fuel_features.populate_fuel_features_for_db, read back by fuel_features.resolve_race_burn_rate(year, gp, db_path) with a fail-safe fallback chain (session → season-mean → DEFAULT_BURN_PER_LAP_KG), and passed into mass_model.race_mass(..., burn_per_lap_kg=<resolved>). mass_model.py stays pure and DB-free — it only gained optional burn_per_lap_kg / max_fuel_kg override arguments whose None defaults reproduce prior behavior exactly; the DB read lives in fuel_features, and layer2/session_race.py (which already reads the DB) does the injection.
  • Wet-excluded. A race with stored session_surface_features.wet_lap_fraction ≥ WET_EXCLUDE_THRESHOLD (0.05) is recorded source='wet_skipped' with a NULL estimate and never contributes to the dry baseline. The wet signal is computed and stored by the data region (compound-based, DB-only); physics only reads it via session_wet_fraction.
  • Primary validation is the compound-free ceiling check. Confidence is measured by race_fuel_ceiling_check (per-race total vs the regulated max fuel), decoupled from tyres/compounds. The lap-time-slope cross-check is retained only as a reference-confounded independent view, not ground truth.

Rationale

  • A zero-fit estimate anchored to a cited regulation cannot silently overfit or drift the way a tuned parameter would; it is auditable against the FIA rule.
  • Keeping mass_model.py DB-free preserves its role as pure arithmetic reusable by the many quali-path consumers; putting the DB read in a separate seam (fuel_features) keeps physics → data the only new coupling and respects the allowed layering direction (data is the bottom layer; data never imports physics).
  • The optional-override design makes the wiring a byte-identical no-op on unpopulated DBs (the resolver fails safe to DEFAULT_BURN_PER_LAP_KG), so the change is invisible to synthetic-DB tests and only moves numerics against real populated season DBs.
  • Wet races are structurally different (rain pace, safety-car neutralisations); excluding them by a stored, named threshold keeps the baseline a clean dry measurement without a magic literal.

Current Structural Consequence

  • New burn-rate consumers must resolve through fuel_features.resolve_race_burn_rate and inject via the mass_model override args — do NOT reintroduce a DB read inside mass_model.py, and do NOT hardcode a burn rate.
  • The estimate is deliberately zero-fit: adding a fitted correction (e.g. the experimental throttle_response_fraction) requires re-opening this decision — that shape is currently off by default and kept only as a documented negative result.
  • Because the rate is now wired into the live W3 mass path, the stored artifacts physics_estimates.db / race_stint_estimates.db are STALE vs the wired rate; a re-batch is a deferred follow-up (Triage), not silently assumed done.

Constraint Impact

  • Bound by constraint:physics_region_no_evo_import — burn_rate_calibration.py and fuel_features.py import no evo-region package (verified).

Rejected Alternatives

  • Fitting a burn-rate parameter (or wiring the experimental throttle_response_fraction saturating shape). Rejected: it did not improve the cross-check, and a fitted knob loses the regulation-anchored auditability. Kept off by default as a negative result so it is not re-reached for.
  • A DB read inside mass_model.py. Rejected: would break the module's pure/DB-free contract and its reuse across the quali path. The read lives in fuel_features; mass_model only exposes an injection seam.
  • Cross-season/circuit pooling of the burn rate. Rejected for now: the per-(season, circuit) estimate is the unit that maps to a race; pooling is not needed for the mass channel and would blur the regulation-anchored per-race quantity.
  • Revising SC_BURN_FRACTION=0.5 from the measured SC/VSC ratio (~0.82-1.01). Deferred, not adopted here — routed to Triage.

Review Trigger

  • Any move to fit/tune the burn rate, enable throttle_response_fraction on a production path, or add cross-season/circuit pooling.
  • A change to mass_model.py that reintroduces a DB dependency, or removal of the burn_per_lap_kg / max_fuel_kg override seam.
  • Revising SC_BURN_FRACTION or DEFAULT_BURN_PER_LAP_KG from measured data.
  • A re-batch of the physics/race-stint stores against the wired rate (clears the STALE-artifacts consequence above).

C1 driver-utilization layer design choices

decision:c1_driver_utilization_design · current · 2026-06-24 · user decision (C1 #510 design session)
Governs: struct:physics.utilization

Question

How should the car/driver split be defined, and what is the denominator for driver utilization? What defines the "ideal lap" for comparison, and who owns the car frontier?

Decision

Four interlocking design choices for src/physics/utilization/ (C1 #510):

  1. Denominator = causal cross-session constructor prior, not season-average and not the driver's own fit. car_prior.build_car_ceiling uses only ok-status sessions at or before the target round W (round_idx <= W), via a one-sided causal kernel. The existing symmetric DriftFit.predict (which leaks future sessions) is explicitly not used here. This makes the car prior a week-to-week-updated through-W estimate — predictive-safe.

  2. Both teammates, including the measured driver, define the frontier. The G1 car ceiling is inferred from the cross-session EstimateStore, which pools both constructor cars' sessions. The driver being evaluated contributed to the frontier estimate. This is the deliberate choice: the frontier reflects the best observed capability of the car as a physical object, not just the other driver.

  3. Car/driver split is acknowledged impure; covariance owns the uncertainty. The car and driver are only ever observed together. regime_utilization.py carries split_is_impure=True on every RegimeUtilization result. Callers must not over-claim separation. The propagated sigma (via MC over ceiling params) quantifies how much of the utilization signal is ceiling uncertainty, not driver skill.

  4. Single canonical ideal-lap path: EstimateStore → car_prior → CapabilityEnvelope → PhysicsSimulator. The inline quasi-static sim_lap / _params prototype in scripts/ideal_lap_compare.py and scripts/ideal_vs_actual.py has been retired (both scripts, and the scripts/ver_monza_kde.py one-off that consumed them, were removed). There is exactly one ideal-lap code path.

Rejected Alternatives

  • Driver's own fit as the denominator: rejected — conflates car capability with driver performance, making utilization trivially ~1.0 for the best driver.
  • Season-average frontier: rejected — blends upgrade steps; the causal through-W prior preserves the temporal structure needed for round-W prediction.
  • Excluding the measured driver from the frontier: rejected — produces systematic under-estimation of car capability for the stronger driver of a pair.
  • A second inline scalar sim: rejected — maintains two diverging code paths; the canonical PhysicsSimulator path is the single authoritative source.

decoupled 1D longitudinal estimator design

decision:decoupled_1d_longitudinal · current · 2026-06-24 · user decision (#496/#507 VERDICT.md GO + G3 two-candidate adjudication)
Governs: struct:physics.layer2

Question

Should longitudinal a_long (the braking-capability input for BrakingView and downstream physics parameters) come from the 2D position smoother's acc_at output, or from a dedicated decoupled 1D physics filter fed by the raw-onset force anchor?

Decision

Longitudinal a_long comes from a decoupled 1D physics filter (decoupled_longitudinal.py) fed by the TV-denoised raw a_long as a tight soft-force anchor on the full braking arc (including the onset sample). The 2D position smoother's output is NOT the source for longitudinal parameters.

The filter works in total mechanical energy / gravity-free vehicle-force coordinates: state [E_total, F_vehicle] over arc-length s, where E_total = ½mv² + mgz(s) and d(E_total)/ds = F_vehicle. A constant-force braking event is a straight line in E_total(s); the brake-onset knee is a benign slope change (kink) rather than a sharp v(t) second-derivative spike that the Matérn prior rounds away. Force is the friction-circle-bounded quantity, so the physics constraints live naturally in this state.

Output: a_long = F_vehicle/m − g sinθ (what the raw sensor measures) + per-sample sigma_a = σ_F/m from the RTS posterior (honest covariance, first-class).

WIRED as of #518 G3 (2026-06-25): session_braking.prepare_braking_frontier now calls build_decoupled_braking_input (the Variant-A adapter) as the ONE canonical braking-frontier input — gravity counted once inside the estimator's z-map; BrakingView's -g sin(theta) term is zero (theta=0 passed in). HP calibration basis: defaults tv_lambda=0.10, sig_a_soft_brake=0.10 swept on 2023-Q VER across Bahrain/Monaco/Belgium and confirmed season-stable across 2023-Q full multi-driver validation (G1); per-session calibration not required at this gate (season-confirmed defaults used).

Rationale

  • decision:smoother_rounds_braking_knee establishes that the 2D position-smoothness Matérn prior is the wrong tool for the longitudinal transient: speed/energy is the only good longitudinal observable (speed shows the ~5.3 g raw peak; position is jitter-dominated; the smoother rounds the braking knee from ~5 g to ~4 g).
  • A decoupled 1D filter (M3) structurally eliminates 2D-coupling ringing (Monaco roc=-0.09 ≤ 0 vs baselines at +7.5/+7.7). The 2D Matérn prior introduces this ringing because the non-throttle phases are coupled through the joint position/velocity/acceleration state.
  • The M7 raw-onset force anchor (TV/IRLS-denoised raw a_long as a tight soft-force obs on the braking arc) recovers the deep braking knee: Bahrain −50.98 m/s² vs raw −52.13 (gap +1.15, down from the +12.7 baseline gap). The onset sample is included (not trimmed as in the plateau-only #498 design) because the raw signal already carries the onset transient and TV preserves rather than invents it.
  • The energy/force reframe is physically sounder: force is the bounded quantity; the brake-onset is a benign kink in energy space, not a spike in acceleration space that the prior must resist. Single canonical path: only the [E_total, F_vehicle] version exists (no [v,a] shim).
  • Scoreboard acceptance simultaneous on both required circuit types (Bahrain hard-braking AND Monaco short-straight ringing) without regressing Belgium — the [v,a] and energy/force formulations are score-equivalent on the a_long metric, so the physically-sounder framing was chosen at no scoreboard cost.

Do not delete it; only the direct frontier read is retired.

  • scoreboard.py is the measurement harness for this and future longitudinal estimator variants; new variants register as VariantFn callables via run_scoreboard.

Decision

Four invariants govern src/physics/layer2/trajectory_refine.py and src/physics/layer2/accel_obs.py:

  1. The anchor is ALWAYS external and un-biased. The acceleration magnitude (inp.a_long) is the raw-sensor total longitudinal acceleration passed in from outside — it is never re-derived from ANY smoothed trajectory (cycle-1 or cycle-2). The heading (vx, vy) from cycle 1 is a geometric frame only; it does not supply the magnitude.

  2. Plateau-only observation placement. emit_accel_obs selects only the established frontier plateau (plateau_margin trims transition samples from each contiguous braking/throttle run). This prevents the kind=3 anchor from pulling against the regime transitions, where acceleration is changing rapidly and ringing would be introduced.

  3. Two cycles only. refine_trajectory runs exactly two cycles. Cycle 3+ with a fixed external anchor buy nothing — the anchor does not change, so additional re-smooths converge at cycle 2. Hard-coding two cycles prevents future scope creep adding a third cycle that could silently re-read a trajectory.

  4. Student-t jerk prior is the cycle-1 foundation. Cycle 1 (nu_proc) retires the Gaussian smoothness assumption before cycle 2 adds the external anchor. The ordering matters: a Gaussian cycle-1 followed by a kind=3 cycle-2 still carries the Gaussian-rounded knee into the heading frame used to project the anchor.

Extension to the 1D-filter context (#496/#507 G3)

The anchor-source discipline (invariant 1 above: external, un-biased, raw-derived) is consciously extended to src/physics/layer2/decoupled_longitudinal.py:

  • Anchor magnitude = the TV/IRLS-denoised RAW a_long (gravity-corrected to vehicle force: m(a_tv + g sinθ) where a_tv is an edge-preserving transform of the raw signal only, never re-read from a smoothed trajectory; the gravity term uses the external #497 z-map gradient, not the trajectory).
  • Anchor placement extended from plateau-only to the full braking arc including the onset sample (the raw signal already carries the onset transient; TV preserves it rather than inventing it; the onset is the capability sample, not noise). This extends invariant 2 for the 1D context where the onset sample is the target.
  • The "two cycles" structure does not literally apply here (this is a single-pass 1D Kalman-RTS, not a 2D re-smooth loop), but the core invariant — the anchor must be re-derived from an INDEPENDENT measurement source, not a prior cycle's output — is preserved exactly.

Question Resolved

Within the tyre-age grip separation model (tyre_separation.py), how should within-weekend track evolution (g_track) be modelled and pooled? The open question was: use the existing cross-session pooling.py random-effects machinery (which pools across constructor × circuit × season), or introduce a new, independent per-circuit slope on cumulative_track_laps with its own partial-pooling?

Decision

g_track(gp, cumulative_track_laps) is modelled as a per-circuit linear slope, partial-pooled across circuits via DerSimonian-Laird τ² (shrinking towards a global mean slope), with a 5× σ inflation for thin circuits (< THIN_MIN = 10 stints). All identifiability and stability checks are leave-one-circuit-out (LOO), so the separation is not self-diagnostic. The existing pooling.py cross-session random-effects machinery is NOT used for g_track.

Rationale

  • pooling.py cross-session pooling is designed for car-parameter random effects (team × circuit × season drift) — it treats the circuit as an exchangeable blocking variable, not an axis of interest. g_track is the WITHIN-WEEKEND track evolution axis; cumulative_track_laps is not a car parameter and has no meaningful pool across constructors or seasons.
  • The separation model requires LOO to be non-trivially testable: a self-inclusive g_track diagnostic over a self-weighted fit would be structurally blind to base↔track aliasing. The per-circuit LOO makes the tyre and track effects genuinely separable (rather than just self-validating).
  • Per-circuit partial pooling (not full pooling) is correct because track-rubbering rates differ by circuit type (abrasive vs smooth; permanent vs street). Full pooling would erase real heterogeneity; no pooling at all would over-fit thin circuits (e.g. Mexico with < 10 stints). The τ² shrinkage is the right middle ground.
  • Thin-circuit σ inflation (5×) is conservative engineering: few stints means weak identification of the per-circuit slope, so the prior is deliberately widened to avoid over-confident separation on poor data.

Current Structural Consequence

  • tyre_separation.py carries its own independent pooling logic (WLS + DerSimonian-Laird τ² over circuits), separate from pooling.py's random-effects/two-way/drift machinery.
  • Agents working on tyre-age or circuit-evolution modelling must NOT substitute pooling.py for the g_track term — the grain and axis are different.
  • The LOO structure of AxisSeparation.loo (LooResult) is the trust evidence for the separation. If LOO RMSE greatly exceeds in-sample RMSE, the base↔track aliasing is active and the separation verdict should be downgraded.
  • Car envelope from the quali store is used RELATIVE (centred within each quali session) so the absolute quali-vs-race grip offset is absorbed by the per-circuit intercept — this is a companion design choice, captured as packet prose in packets/physics.md.

Rejected Alternatives

  • Use pooling.py cross-session random effects for g_track: pooling.py groups by constructor × circuit; the cumulative-track-lap axis is a within-weekend covariate, not a cross-session car parameter. Substituting it would conflate within-session rubbering with between-session car development.
  • No g_track term (omit track evolution): without a g_track absorber, circuit-specific rubbering leaks into the f_tyre compound k estimates — circuits that rubber in fast would show artificially high k, circuits that don't would show low k, contaminating the compound ladder.
  • Full cross-circuit pooling (single global slope): erases the real heterogeneity in rubbering rates across circuit types (abrasive high-deg circuits vs smooth street circuits); the τ² estimate from the partial-pooling fit reveals this heterogeneity is real.

Review Trigger

  • If tyre_separation.py g_track LOO shows systematic over-fit (oos_rmse >> in_sample_rmse) for a new season or circuit, revisit whether the partial-pooling τ² prior is well-calibrated.
  • If the race-stint store adds new session_type values beyond 'R', confirm the g_track slope is still meaningful for those session types before reusing it.
  • If pooling.py is extended to support within-session covariate axes, evaluate whether the two implementations should be unified.
