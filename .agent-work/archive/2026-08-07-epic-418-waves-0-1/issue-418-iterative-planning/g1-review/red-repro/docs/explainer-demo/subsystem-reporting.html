Detail (from the Cartographer packet)

Mixed status. This container is no longer a uniform dead path. The MC-era report generators (race_report/, visualizations.py) are stale, but html_reports/ is a current, live subpackage that renders dashboards from the live evo gold-cycle artifacts.

Responsibility

Generates race prediction and pipeline reports. Two distinct cohorts live here:

  • html_reports/ (current). Self-contained dark-mode HTML dashboards over live pipeline output — no Monte Carlo dependency.
  • race_report/ + visualizations.py (stale). Markdown/HTML/JSON reports built from the dead Monte Carlo simulation path.

Key Modules

html_reports/ — HTML Dashboard Generator (package, current) Standalone HTML report generator (added in PR #346, commit f179775). Embeds all data as inline JSON; no server required. Entry points: py -m src.reporting.html_reports (__main__.py) and scripts/gen_html_reports.py (runs without torch/fastf1). Split across _theme.py (palette/CSS), _primitives.py (HTML building blocks), _module_cards.py (module cards, run-comparison table, fusion section), and one report_*.py per report; __init__.py re-exports the public builders:

  • generate_gold_cycle_report — reads reports/evo/gold_cycle_*.summary.json
  • generate_training_data_report — training-data coverage from the season DBs
  • generate_alignment_report — predictive↔retro alignment per gold slug
  • generate_index / generate_all

Reads its inputs directly: gold-cycle JSON from reports/evo/ and the season SQLite DBs via raw sqlite3.connect, funneled through the single sanctioned _connect_report_db helper (it does not route through src.data.database.DatabaseManager — a deliberate dependency-light choice so the generator runs without the analysis stack; see the Decision note under Trust limitations).

race_report/ — MC Race Reports (package, stale) RaceReportGenerator (in race_report/generator.py) formats race prediction reports into Markdown/HTML/JSON (markdown.py, html_report.py, json_report.py, actuals.py). Reads src.data.database and src.models.data_models, and lazily imports src.strategy.scoring.ScoringCalculator for scoring. Part of the legacy MC report path; not driven by the live evo pipeline.

visualizations.py (stale) Visualization generation: score distributions, win-rate heatmaps, backtest time series. Publication-quality at 300 DPI. MC-era.

Dependencies

  • html_reports/ → struct:sqlite_db (raw sqlite3) and live reports/evo/ artifacts (read-only)
  • race_report/ → struct:data, struct:models, and lazily struct:strategy (scoring)

Notes

  • The earlier "whole package is a dead path superseded by gold-cycle reports" claim is no longer true: html_reports/ is a consumer of the live gold-cycle reports.
  • Live evo predictions/backtests are still produced by the gold cycle and the sampled-runtime CLI, not by race_report/.

Trust limitations

  • html_reports/ reads the canonical season DBs with raw sqlite3.connect, bypassing DatabaseManager. The DB-only-source constraint holds (it reads the canonical store); only the data-layer access object is bypassed. This is a blessed bypass — see the Decision note below.

Decision (issue #351): bless the raw-sqlite3 bypass

Resolution: keep the raw-sqlite3 read path; do not route html_reports/ through DatabaseManager. Adopted 2026-06-02.

Rationale:

  • html_reports/ is intentionally dependency-light. scripts/gen_html_reports.py goes out of its way to load the module directly via importlib, bypassing src.reporting.__init__, precisely to keep the import graph minimal, and its docstring advertises "runs without torch/fastf1". Importing DatabaseManager would pull numpy + pandas + Config into that graph, undermining the deliberate design the code already protects.
  • The DB-only-source tenet is not violated: reads target the canonical season stores. Only the access object is bypassed, which is acceptable for a read-only standalone generator.

Hardening applied: all raw connections now funnel through one local helper, _connect_report_db (in html_reports/report_training_data.py), which documents the blessed bypass and is the single place a connection is opened. Future readers should reuse it rather than calling sqlite3.connect directly.
