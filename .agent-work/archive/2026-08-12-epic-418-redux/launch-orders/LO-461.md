## Mission

Issue **#461 — "the episode-store negative control fails every run that legitimately captures an
episode, between git add and commit"**.

`tests/test_episode_negative_control.py::test_canon_episode_store_untouched` exists to catch a **test
run** accidentally writing into the canon store. Its assertion is broader than that intent:

```python
dirty = subprocess.run(["git", "status", "--porcelain", "episodes/"], ...).stdout.strip()
assert dirty == "", f"canon episode store is dirty: {dirty}"
```

Its own docstring frames the property as *"the working tree agrees with the index"* — worktree-vs-index.
But `git status --porcelain` **also** reports index-vs-HEAD, so a staged addition fails it:

```
canon episode store is dirty: A  episodes/active/issue-447-008.md
```

**Deliverable:** the assertion tests worktree-vs-index only, so a staged-but-uncommitted legitimate
capture passes while stray writes still fail — and the docstring's stated property and the code's
actual predicate agree.

## Why it matters, and why it is not cosmetic

This lands on a gate **every Commander now passes through.** `verify_episode_captured.py --phase
archive` requires the episodes to be tracked, so the ordering `write → git add → suite → commit` is
the normal path, and the suite is **red in the middle of it**. The #447 spine mandates
`git add episodes/` before the archive-phase capture gate can pass, so **the window is structural,
not incidental.** A crew that meets this without context reads it as a regression it caused.

It was observed live in epic-418 workstream H (#447) g4 — the first run to write episodes into canon
— raised as a blocker, and closed only by the Commander's integrate commit.

**The Admiral reproduced it first-hand during #460's merge in wave 2**, which is why it was held to
this wave rather than dropped.

## The trap in this issue — read this before you touch the assertion

The control is **not broken and must not be loosened carelessly.** After the commit, all three of
worktree, index and HEAD agree, so the current emptiness is honest, and the control's anti-vacuity
guard genuinely strengthens as the store grows. It is easy to "fix" this by weakening the assertion
until it stops complaining — and a weakened control still passes every green run, so nothing tells
you that you broke it.

**That is exactly this wave's organizing defect: a check whose value is identical in the healthy and
defective worlds.** Wave 2 found four instances of it across four subsystems. Yours would be a fifth.

So the acceptance criteria are written as **falsification, not assertion**:

- A **stray unstaged write** under `episodes/active/` still fails the control.
- A **stray untracked file** under `episodes/active/` still fails the control.
- A **staged-but-uncommitted legitimate capture** passes.

Observe all three. Paste the failures. A return that says "narrowed the predicate, suite green" has
not done this dispatch — green proves nothing here, because green is what the broken version does too.
