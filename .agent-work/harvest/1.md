**Surfaced by the constellation feedback harvest (2026-06-24).** The engine session lease goes stale (default `lease_stale_seconds=1800`) and the next mutating verb is REFUSED until a re-claim. This is the single most-recurring finding across the dogfooding fleet — **~5 occurrences in all 3 projects** — currently fragmented across 4 fingerprints because of slug drift (no shared `Lesson:` id).

### Occurrences
- **f1Brainz** `spine-lease-stale-on-long-crew` — issue-446: `advance execute` refused stale after the g3 multi-session crew; re-claimed `--force --reason`.
- **f1Brainz** `spine-lease-stale-on-long-crew-step` — issue-448-fix1: ~8 min g5 competition re-run lapsed the lease mid-spine (2nd occurrence in lineage).
- **network_elo** `session-lease-staleness` — lease stale after ~30 min idle between turns; re-claim with same id required.
- **story_time** `engine-could-auto-heartbeat-on-mutating-verbs` — stale at the execute→closeout boundary on a long autonomous Admiral run; idempotent same-id re-claim recovered it.

### Cost
Every multi-minute / long-idle run risks a spurious stale-lease refusal; each is worked around with a `--force` / same-id re-claim that reads as a takeover in the audit trail.

### Proposed fix (story_time framing — cleanest)
The checklist engine refreshes `last_heartbeat` automatically on any successful **mutating verb** (start/advance/attest/attach) by the lease-holding session, so an actively-working session never goes stale. Reserve explicit `heartbeat` for genuinely idle waits. At minimum, document that "re-claim with the same id is idempotent, not a takeover."
