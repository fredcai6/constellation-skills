=== THE ONE THING: corpus-shape trap ===

The crew's own admission is accurate: superCoolSpaceSim (0 .py files) was a null test, so only
f1Brainz exercised the F9 trap (~75% test code). I found the trap fires on a corpus already IN
HAND -- this repo's own real, already-built map/INDEX.md -- and confirmed it in isolation with
two synthetic shapes.

REAL EVIDENCE, no synthesis needed (map/INDEX.md, fresh build this run): this repo's own
`tests` package is 50 modules / 2769 entities = 74.3% of the corpus's 3728 entities -- the SAME
proportion F9 named as the trap. It is a completely FLAT directory (every module is
`tests.test_foo`, two dotted segments). The tier predicate `len(m.split("."))>=3` never fires
for a single one of its 50 modules, so `## tests` renders as 50 undifferentiated `- [...]`
bullets with ZERO subheadings -- read it yourself: `map/INDEX.md` lines 89-140. This is the
exact flat-list failure mode the gate exists to fix, unaddressed, on the crew's own flagship
corpus, in the single bucket holding three-quarters of the repo. The crew's own
g4_tier_shape.md evidence only measured tier-1 sizes for constellation-skills (12/54, 49/905,
50/2769) and never looked at tier-2 behavior on this corpus at all -- if they had, they would
have found this.

SYNTHETIC CONFIRMATION, isolating the mechanism (`.agent-work/issue-456/evidence/
g4_reviewer_synth_corpora.py` + `.txt`, built into scratch temp dirs, nothing tracked touched):

  Shape A -- one flat package, 30 modules, zero nesting (the pytest-default layout: everything
  in one directory, no subpackages -- this is what `tests/` above IS, isolated from f1Brainz's
  mixed structure). Result: `## flat (31 modules, 30 entities)` followed by 31 loose bullets,
  0 `###` headings. Tier 2 provides no benefit whatsoever for this real, common shape.

  Shape B -- loose top-level modules, no packages at all (named explicitly in the handoff as a
  shape to try). Result: TIER 1 ITSELF degenerates. `BY_PKG` keys off `m.split(".")[0]`, so
  when every module has exactly one dotted segment, every module becomes its own "package."
  The `## packages` overview -- whose whole design rationale, stated in `top_index`'s own
  docstring, is "bounded by how many top-level packages the corpus has, never by how many
  modules" -- becomes a 30-line, one-package-per-module list, a 1:1 restatement of the module
  list it sits above. That docstring claim is FALSE for this shape. The crew's own evidence doc
  states "none is 'N buckets of one' (superCoolSpaceSim correctly reports nothing to route, not
  N empty headings)" -- but superCoolSpaceSim (0 modules) cannot exercise "N buckets of one" at
  all; it can only ever produce the single "no mappable modules found" line. Shape B is the
  actual "N buckets of one" case and the claim does not hold for it.

VERDICT ON THE SHAPE: both are REAL, not pathological. Shape A is this repo's own `tests/`
directory and the default pytest layout used across the ecosystem. Shape B is a small
script-bag repo with no package structure -- also common (single-purpose tool repos, ML
training scripts, most tutorial/demo repos). Neither is contrived to break the code; both are
ordinary layouts a code_map user will actually point this at.

Is this a blocker? I judge NOT, for three reasons: (1) the tier remains DERIVED, not TUNED --
it does not fabricate structure that isn't there, it honestly reports "nothing to group,"
which is what the crew's own docstring claims for the flat case (true) even though the
docstring's SEPARATE bound claim about tier 1 is false for shape B; (2) no test and no close
criterion asserts the tier eliminates the flat-list problem for EVERY shape -- the close
criterion is "derived, not tuned, shape reported per corpus," which holds; (3) nothing crashes,
corrupts, or produces a misleading/wrong index -- it produces an honest, if unhelpfully
granular, one. This is a real gap in the gate's stated purpose ("ROUTE, not list") for a
common corpus shape, filed as a triage candidate below, not a blocker.
