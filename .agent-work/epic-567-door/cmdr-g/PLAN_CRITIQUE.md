# Plan Critique — cmdr-g `finish_work` (Candidate B)

Read cold, against source on the base commit. Triaged Serious / Minor / Nitpick.

## Serious

### 1. `finish_work`'s own first gate refuses on every normal call — the composition is dead on arrival
PLAN_CANDIDATE_B.md g3 (lines 43-52) orders the sequence:

> verify (`done_refusal` on the CURRENT state) -> `_advance_and_release` -> re-verify (`done_refusal` again, now expecting released+terminal, i.e. `closeout_refusal`'s own check) -> `force_reap` -> ...

and g1 (lines 13-17) defines `done_refusal` as: "wraps `closeout_refusal`'s terminality/lease checks (reused, not re-derived) plus two new checks."

`closeout_refusal` (`scripts/spine_lifecycle.py:122-161`) refuses on its very first predicate — `status != "released"` (line 143-144) — before it even looks at gate terminality. The state `finish_work` is invoked on is, by definition, an *active* lease: the agent has just said "I'm done" and has not released yet — that's the whole point of composing `_advance_and_release` into one call. So the FIRST `done_refusal` call in g3, running `closeout_refusal`'s lease check against a still-active lease, returns `"close refused: the lease is still active"` on every legitimate invocation, before `_advance_and_release` (which would actually release it) ever runs.

As specified, `finish_work` cannot complete a single real closeout: its own first verify step trips on the exact condition the rest of the function exists to fix. Either the plan needs a second, narrower predicate for the pre-advance check (checking only the two new conditions — tree_clean, episodes_captured — not the closeout_refusal-derived lease/terminality checks), or the ordering/composition described in g3 is simply wrong. Nothing in g1 or g3 documents a mode/parameter on `done_refusal` that would select which sub-checks apply at which call site, so this isn't a documented, deliberate two-mode design — it reads as an oversight in the convergence write-up itself. This should block acceptance of Candidate B as currently spelled out; it is not a nitpick about wording, it is a function that provably cannot return `None` on its intended happy path.

### 2. `force_reap` runs before `_release_child_plans` — the #552 fix the plan claims to deliver is only half-applied within one call
PLAN_CANDIDATE_B.md g3 orders `force_reap` *before* `_release_child_plans`. `force_reap` is `spine_rail._binding_transaction(project_dir, lambda reaped: reaped)` (g2, lines 30-34), which forces `_reap_binding_entries` (`scripts/hooks/spine_rail.py:311-366`) to run and persist immediately. `_reap_binding_entries` only drops a binding-store entry whose target spine currently reads `engine_session.status == "released"` (spine_rail.py:349-355) — every entry whose target is still `"active"` is kept (line 354, `kept[abs_spine] = entry`), regardless of age.

At the point `force_reap` runs in this ordering, the top-level spine has just been released by `_advance_and_release`, so its own binding entry (if any) is correctly swept. But any child plan is still `active` at that moment — `_release_child_plans` hasn't run yet — so the reap pass leaves every child's binding-store entry exactly as stale as it was before `finish_work` was called. Those entries only get cleaned up on some *future, unrelated* binding-store transaction — which is verbatim the mechanism MISSION_FRAME.md line 14 names as "the literal mechanism behind #552's '17 stale leases inside `archive/`' measurement," and which the mission (line 6) explicitly claims this run closes ("archives the work area (including child plans' leases -- the #552 gap)"). The order as written does not close that gap for the binding store, only for the spine content (which `_release_child_plans` does update). Swap the order — release children, then `force_reap` once, at the end — and the immediate-reap guarantee actually covers the case the plan says it covers.

### 3. The interrogation record's "release as last journaled action" premise is false of the base engine, before this plan touches anything
`INTERROGATION_RECORD.json` q3-close-shape asks exactly this: "Can 'final advance + release as last journaled action' be built...?" and resolves "Yes... `main()` composes load->dispatch->save->journal," citing `checklist_engine.py:1133 (release), :2468 (advance), :3495 (main)`. MISSION_FRAME.md line 27 repeats this as a governing assumption.

It doesn't hold. `release` is excluded from `MUTATING_VERBS` (`checklist_engine.py:70-74`: `{"start", "advance", "record", "consolidate", "skip", "block", "resume", "reopen", "append", "attest", "waive", "attach", "flag-candidate", "amend"}` — no `"release"`), and `main()` only calls `append_journal_entry` `if args.verb in MUTATING_VERBS` (`checklist_engine.py:3599-3604`). `release` also dispatches through an early, separate path in `dispatch()` (`checklist_engine.py:3305-3309`) that never touches the journal machinery. `release` *does* still get persisted to `spine.json` — `save(path, cl)` at line 3595 runs for every verb except `current`/dry-run — but it produces **no journal line**. This is true today, independent of this plan; the interrogation's own code-evidence citation (release/advance/main line numbers) never touched the `MUTATING_VERBS` set (line 70) or the journal gate (line 3599) that falsifies its conclusion.

Consequence: the real "last journaled action" after `_advance_and_release` runs is the **advance** call, not the release — the journal simply has no representation of the release event at all, mechanical marker or otherwise. Any test or downstream expectation built on "the journal's last entry names the release" will fail; any doc claiming closeout leaves a journal trail ending in release is inaccurate about what the engine actually records. This should be corrected in the plan's own foundational assumptions before g1/g3 are implemented and tested against it.

## Minor

### 4. In-process `main(argv)` reuse is under-specified next to its only real precedent
Both candidates describe calling `checklist_engine.main([...])` in-process as "the existing pass-through pattern" (PLAN_CANDIDATE_B.md g1, line 22-24; MISSION_FRAME.md line 35). The only place that pattern actually exists in this codebase is `scripts/mcp_spine_server.py:664-685`, which wraps the call as:
```
with contextlib.redirect_stdout(out), contextlib.redirect_stderr(err):
    ...
    code = checklist_engine.main(argv)
except SystemExit as exc:  # argparse rejected the argv
    code = int(exc.code or 0)
except Exception as exc:
    code = 1
    err.write(...)
```
`parse_args` (`checklist_engine.py:3181-3281`) is plain `argparse`, which calls `sys.exit()` on a malformed argv — that's a `SystemExit`, not a caught `EngineError`, and it happens *inside* `main()`, before `dispatch()`. Candidate B's prose ("Returns the two captured (stdout, exit code) pairs untouched") implies awareness that capture is needed, but never mentions `redirect_stdout`/`redirect_stderr` or the `SystemExit` catch that its cited precedent actually relies on. Since `finish_work` constructs its own argv (not user-typed), the risk of ever hitting this is low, but it is not zero (e.g. a `mechanical=True` path that still forgets to convert `--mechanical` into a real flag rather than a truthy string), and an uncaught `SystemExit` there would propagate out of `finish_work` as a raw interpreter exit rather than a graceful refusal — undercutting the "one call, always a clean result" contract the plan is selling. Worth naming the reused mechanics explicitly, not just the module-level "pattern."

### 5. The "re-verify" `done_refusal` call partly duplicates a check `close_work` runs again immediately after
g3's step after `_advance_and_release` is "re-verify (`done_refusal` again... i.e. `closeout_refusal`'s own check)," and the very next step, `close_work` (unmodified), computes and applies `closeout_refusal` itself (`spine_lifecycle.py:453-455`) before doing anything. The lease/terminality/archive-exists portion of the re-verify call is fully redundant with what `close_work` will do a few lines later — only the two *new* checks (`tree_clean`, `episodes_captured`) that `done_refusal` adds on top of `closeout_refusal` earn their keep at that point. Not wrong, just an extra file read/parse and a duplicated refusal path for no additional coverage; if `done_refusal`'s two new checks were split into their own predicate, `close_work`'s existing `closeout_refusal` call could be the sole terminal/lease check, one file read narrower.

### 6. `_release_child_plans`'s "ownership" check is a self-referential no-op, not a real authorization
Candidate B g2 (line 37-38) says `_release_child_plans` "calls `_advance_and_release`'s release half on each via its own session id" — i.e. it reads the child's own recorded `engine_session.session_id` back out of the child's file and hands that same value to `release()`. `release()`'s ownership gate (`checklist_engine.py:1139-1143`, `if session_id != sess.get("session_id") and not force`) trivially passes whenever the caller supplies the value it just read from the same record — this is not verifying that `finish_work`'s caller is entitled to release the child, it is mechanically impersonating whoever last claimed it. That may well be the *correct* behavior for a closeout sweep (children left behind at archive time generally should be force-cleaned), but the plan doesn't say so — it should either call this out as a deliberate, unconditional force-release (and arguably use `release(..., force=True, reason="closeout: child plan swept by finish_work")` so the resulting record is honest about what happened), or explain why self-supplied-session-id is preferred over `--force --reason`.

## Nitpicks

### 7. Internally inconsistent test-fixture description in g1
PLAN_CANDIDATE_B.md line 25-26 describes a test fixture as "a fixture spine at its terminal gate but not yet advanced." `TERMINAL` (`checklist_engine.py:63`, `{"complete", "skipped"}`) already means *advanced* — a gate can't simultaneously be "terminal" and "not yet advanced." The intended state is presumably "postconditions satisfiable, task still `in-progress`" — worth tightening before someone implements the fixture literally as described.

### 8. "Already-proven-safe" framing overstates precedent for the stdout-capture technique specifically
MISSION_FRAME.md line 35 says the library-reuse pattern "mirrors the pattern `spine_lifecycle.py` already uses for `generate_spine`/`init_work_area`/`run_crew`/`validate_spine`." Those four are plain Python function imports called directly (no argv, no stdout capture, no subprocess-shaped boundary) — see `spine_lifecycle.py:43-47` imports and their call sites in `open_work`. The actual precedent for the argv-in/stdout-captured-out technique this plan needs for `_advance_and_release` exists only in the fenced `mcp_spine_server.py` (finding 4, above), a different module with a different risk profile (server-process lifetime, MCP tool boundary) than `spine_lifecycle.py`'s existing direct-import callers. Not the same kind of "already proven" the mission frame implies; worth citing the real precedent (mcp_spine_server.py:664-685) rather than the four unrelated direct-import callers.

### 9. `tests/test_spine_lifecycle.py`'s own existing end-to-end pattern doesn't use `main(argv)` either
`TestCloseWorkEndToEndRealEngine` (`tests/test_spine_lifecycle.py:1141-1178`) drives claim/advance/release by calling `checklist_engine.claim`/`release` and `checklist_engine.save` directly as library functions on an in-memory dict, never through `main(argv)`. That's the right call for *that* test (it needs a hand-built two-gate spine, not journal fidelity), but it means Candidate B's g1/g3 tests, which need to assert on `main(argv)`'s captured stdout/exit code, are introducing a genuinely new test technique to this file rather than following an established local convention — worth flagging so the implementer doesn't assume there's a copy-paste starting point already in this file (there isn't).

### 10. Candidate A's stated risk becomes the practical fallback given finding 1
Candidate A's own risk section (PLAN_CANDIDATE_A.md line 63-67) concedes it "is the smallest diff, not the smallest gap" because it doesn't drive `advance`. Given finding 1 above (Candidate B's `finish_work` cannot currently complete a real closeout as speced), Candidate A — which never introduces the self-refusing first `done_refusal` call, because it doesn't call `_advance_and_release` at all and starts from an already-released precondition — is, in its current written form, the only one of the two that is actually runnable end-to-end today. That doesn't make A the right target architecture, but it's worth the plan owning explicitly: B's "wins depth and seam placement outright" framing in PLAN_ALTERNATIVES.md line 18 is only true once finding 1 is fixed.
