# Critique — testability lens

## Findings table

| ID | Lens | Severity | Finding | Disposition | Reason |
|---|---|---|---|---|---|
| T1 | testability | BLOCKING | The falsification story for workstream A (10 dedup moves, the largest) does not hold. Testing pathway 1 claims "a move that drops a doctrine from a role's runtime view fails the bundle/content tests." The bundle tests assert only that a `global-*.md` *file* is present in a skill's `references/` (test_install_constellation.py:196–208, :231–241); they never inspect its content. The suite content-pins exactly one doctrine string, "Deep-module vocabulary" (test_install_constellation.py:690). A reconcile-then-cut that drops, truncates, or mangles any of the other ~9 relocated doctrines leaves every test green. The only detector that would actually fire is the manual post-move grep — a human step, not an automated test — so the workstream with the most moves has essentially no mechanical regression net. | | |
| T2 | testability | MAJOR | The grep that the whole dedup safety story leans on is self-referential and unenforced. Section A constraints say "confirm carrier list by grep against final wording." The grep pattern is chosen by the same agent performing the cut; a carrier whose inline copy drifted far enough to miss that pattern is precisely the one that gets silently left behind or dropped — the under-inclusive-attribution failure the project already paid for ([[derive-distribution-claims-from-command]]). Nothing forces the grep to be run, and no evidence contract mechanism captures/retains its before/after output. "Each dedup PR carries the grep-derived before/after carrier counts as evidence" is a human-discipline promise with no backing check. | | |
| T3 | testability | MAJOR | Project Euler answer leakage undermines the harness's headline check. The runner's first listed check is "answer correct" (spec §E, line 93). Frontier models very likely have Euler answers memorized, so a crew can emit the correct number without the commander→implementer→reviewer spine, handoffs, or evidence discipline actually functioning. The genuinely diagnostic checks (spine JSON completed its steps, expected artifacts present, tests green) are listed but not privileged. The spec never states that answer-correctness is a near-worthless workflow signal and that the mechanical/process checks must carry the verdict — so as written a scenario can pass with the workflow machinery half-broken, which is the exact opposite of what the harness exists to detect. | | |
| T4 | testability | MAJOR | A single headless-agent run cannot falsify a skill regression. The runner "launches one fresh headless agent on the scenario" and computes a verdict (§E, line 93). LLM agents are stochastic; one run cannot separate a real regression from run-to-run variance. The falsification claim in Testing pathway 3 ("checks pass with a known-broken skill / fail with a known-good one") requires repeated runs and a pass-rate threshold to be meaningful, and the situational bar of "≥1 fresh-context eval run" (§E line 95) is exactly one run. A flaky green is indistinguishable from a true green, so the harness's own acceptance signal is not reproducible. No determinism controls (seed, temperature, N-of-M, reton threshold) are specified. | | |
| T5 | testability | MAJOR | The curator's acceptance criterion is circular. Testing pathway 2 makes the first curator report's near-quietness "itself the acceptance evidence." But the duplication-signature detector in `curate_corpus.py` and the A/B/F fixes share one author and one model of what "sediment" is; the curator is quiet on exactly the patterns it defines as sediment — the ones A/B/F already targeted — by construction. Quietness proves the detector and the fixes agree, not that the corpus is clean. Any class of real duplication the signature doesn't model is invisible to both the fix pass and the acceptance check, so the criterion cannot fail for the reason it purports to guard. | | |
| T6 | testability | MAJOR | The curator golden-file test only exercises what the fixture plants. `curate_corpus.py`'s load-bearing novelty is duplication-signature clustering plus description lint; a golden file over a hand-crafted "known-bad skill dir" (Testing pathway 2) validates those detectors against the fixture's planted flaws only. If the fixture does not reproduce the real corpus's duplication shapes (the ones x2 measured), the detector can miss real dupes while the golden test stays green. The spec states no contract that the fixture mirror the measured failure modes, so golden-file coverage and real-corpus coverage are decoupled. | | |
| T7 | testability | MAJOR | "Description lint" is claimed as deterministic but its criteria are semantic. Invariant #1 (§C, line 74) has the script decide "when-to-use present; procedure absent; third-person." Distinguishing a procedure from a triggering-condition, and second- from third-person, over free-form prose is NLP-hard. Either the lint is a shallow keyword/regex check — which will misfire on real descriptions and is trivially gamed — or it needs judgment, which breaks the "deterministic → golden-file test" premise the very same pathway relies on. The spec asserts determinism without specifying what makes "procedure absent" mechanically decidable. | | |
| T8 | testability | MAJOR | Workstream F ships an untested selection behavior, and it is the same failure mode the spec elsewhere rejected. The entire purpose of the commander / commander-delegated split is that each entry's description plus exclusion clause ("do NOT use when a human is driving," and its inverse) routes the correct invoker. That is a description-selection behavior — exactly what the install tests cannot observe (they check file presence and the no-`global-*.md` rule, §F line 106). The rejected-approaches list killed "pushy descriptions" because "suite siblings would steal triggers"; two near-identical commander entries are a textbook trigger-collision, yet F's only near-term verification is "a fresh-context read of each entry skill" (Testing pathway 4) — vibes — with the real eval deferred to E's gate. F can regress selection and nothing mechanical catches it. | | |
| T9 | testability | MAJOR | The design's tailoring/register half rests on unfalsifiable vibes criteria. "Every SKILL.md reads as one deliberately-written document absorbable in a single pass" (Intent), "body register matches" the invoker tag (cross-cutting rule 4), and "emphasis only at mechanism-backed gates" (rule 2) have no check. The curator lints invoker-tag *presence* (Invariant #1) but not that register matches the tag, and soft budgets are explicitly flags-never-gates (rule 5). So the doc-coherence, register, and invoker-tailoring goals — a large fraction of "done feels like" — can only be judged by inspection and can never be falsified. "Done" for that half of the spec is a matter of opinion. | | |
| T10 | testability | MINOR | The confirm gate verifies form, not substance, and the spec leans on it harder than it can bear. `verify_spec_confirmed.py` only checks that no Disposition cell is empty and that Status/Confirmed-by/Date are filled (verify_spec_confirmed.py:140–171). Every cell reading "N/A" or "won't-fix" passes; a disposition that waves off a BLOCKING finding passes. The spec calls "the filled block plus the downstream refusal" the mechanical backstops (Confirmation note), but that backstop guards presence, not quality of triage — worth stating plainly so the gate is not mistaken for a substantive review. | | |
| T11 | testability | MINOR | The only pathway that exercises real runtime behavior is optional and sequenced last. Cluster E gates on nothing ("nothing gates on evals," §E line 95) and is explicitly "tackle last"; Cluster F defers its behavioral test to E's gate (Testing pathway 4). Net: A–D complete and F (a behavior-changing restructure) can ship with the eval harness — the sole behavioral falsification mechanism — never built. If E slips or is dropped, the corpus has been restructured with zero behavioral regression coverage, only structure tests and human reads. The sequencing makes the design's one real test the easiest thing to cut. | | |

## Notes

- **T1** — Verified against `tests/test_install_constellation.py`. `test_global_doctrine_buckets_bundled_per_audience` (lines 180–208) asserts the *set of filenames* matching `global-*.md` per skill; `test_windows_md_bundled_alongside_global_everyone` (lines 210–241) asserts `windows.md` and `global-everyone.md` are files that exist. Neither reads bucket content. The single doctrine-content assertion in the whole suite is `test_deep_module_vocabulary_ships_into_installed_skill` → `assertIn("Deep-module vocabulary", vocab)` (line 690). The `assertIn("Global doctrine", ...)` at line 272 only proves the force-refresh rewrote *something*, not that any specific doctrine survived. So the spec's "fails the bundle/content tests" (Testing pathway 1) is contradicted by the actual suite: the bundle tests are structural, the "content tests" are one string. This is the load-bearing safety claim for the 10-move A cluster.

- **T2** — Section A "Constraints (contractual)" and Testing pathway 1. The grep is the real detector once T1 shows the suite is blind to content; but the grep is authored ad hoc per move and its running/output-retention is not enforced by any spine step or script. Contrast the enforced evidence contracts elsewhere (e.g. `verify_agent_feedback.py`, `verify_spec_confirmed.py`) — the dedup evidence has no such backstop.

- **T3 / T4** — Spec §E lines 92–96 and Testing pathway 3 (line 125). Both are properties of using a live LLM agent as the system under test; the spec treats the harness as if the verdict were a pure function of the skills, which it is not. T3 is about the check being too weak by leakage; T4 is about the verdict being irreproducible. The runner script `run_skill_eval.py` does not yet exist (proposed), so these are design-time gaps to fix in the deferred runner-contract gate, but the spec should name them now rather than assert "verdict is computed" as if that settles trust.

- **T5 / T6 / T7** — Cluster C, §C and Testing pathway 2. `scripts/curate_corpus.py` is proposed, not present. T5 is the circularity of self-consistent acceptance; T6 is fixture/real-corpus decoupling; T7 is the semantic-vs-deterministic tension in the lint. All three converge on: the curator's verification story assumes the hard part (defining sediment, detecting procedure-in-prose, matching real duplication) is already solved by the same script whose correctness is in question.

- **T8** — Cluster F, §F lines 100–107, and the rejected "pushy descriptions" entry in the exploration digest (line 32: "suite siblings would steal triggers"). The install-mechanics assertions the spec cites (per-skill bundle map / core-ref must-not-match `global-*.md`, precedent at test lines 196–208) verify plumbing, not routing. Routing is the risk; routing is untested until E.

- **T9** — Intent (line 22), cross-cutting rules 2 and 4 (lines 114, 116), Invariant #1 (line 74). The invoker-tag *presence* check is real; the register-matches-tag and single-deliberate-document claims are not checkable as specified.

- **T10** — `scripts/verify_spec_confirmed.py:140–171`, confirmed by reading. The gate is exactly a non-empty-cells + filled-fields check. Test coverage (`tests/test_verify_spec_confirmed.py`) confirms it tests emptiness/marker/fields, nothing about disposition quality. The spec is candid about this (line 16) — flagged MINOR only so the reader does not over-trust it.

- **T11** — §E line 88 ("tackle last"), line 95 ("nothing gates on evals"), Testing pathway 4 (line 126, F's behavioral test deferred to E). Sequencing is presented as "guidance, not a cut" (line 37), which makes the one behavioral test the most droppable item.
