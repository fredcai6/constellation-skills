# Critic result — simplicity/YAGNI

Lens: `simplicity/YAGNI — what can be deleted`. Cold review of `DESIGN_SPEC.md` only.

Disposition and Reason are left empty by design — the critic does not self-triage.

| ID | Lens | Severity | Finding | Disposition | Reason |
|---|---|---|---|---|---|
| S1 | simplicity/YAGNI | BLOCKING | Workstream F (MCP front door) is the largest deletable unit in the spec, and its own evidence does not support it. The spec states that part of the measured win came from teaching sentences written into tool descriptions rather than from MCP structure, and that the control arm which would have separated the two was skipped by ruling. So the claim "MCP structure caused the improvement" is currently unfalsified, and the cheaper alternative that captures the same measured effect — write those teaching sentences into the CLI help text and the gate imperatives — is never costed or ruled out. Against that, F permanently adds a second front door to the engine, ~1,000 always-loaded tokens, and a known lease-identity regression whose fix ("how a freshly dispatched subagent gets its own instance") is admitted to be unsolved. Delete F from this spec, ship the teaching text through the existing door, and re-propose F only if the text-only change fails to reproduce the win. |  |  |
| S2 | simplicity/YAGNI | BLOCKING | Workstreams C and F push in opposite directions and the spec never reconciles them. C's stated purpose and acceptance measure is shrinking always-loaded prose; F knowingly adds ~1,000 always-loaded tokens of schema plus rich, always-loaded tool descriptions carrying instruction text. F asserts "no second rendering path exists" because the gate imperative rides tool results verbatim, but that only covers imperatives — the tool descriptions are themselves a third always-loaded instruction surface alongside role prose and spine imperatives, and the CLI door is explicitly retained, so instruction text must be kept correct in all of them forever. Pick one delivery channel for this stage. Shipping both means the epic's net always-loaded token delta may be positive while C reports success on its own narrow count. |  |  |
| S3 | simplicity/YAGNI | MAJOR | Workstream A repairs a mechanism the spec never justifies keeping. The governor "still produces zero readings on live runs" — it has never worked in production — and repairing it now costs an identity module, a documentation correction in a load-bearing place, and a 47-binding sweep. Nowhere does the spec name what consumes a gauge reading: which agent, at which moment, changes which decision because a context fill was written down. The one place a consumer is discussed cuts the other way — metrics methodology is parked because "token load survives only inside the governor, which is its one customer," which names the governor as a consumer of metrics, not any consumer of the governor. Delete A until a reader of the readings is named, or state the consumer in the spec so the workstream can be sized against it. |  |  |
| S4 | simplicity/YAGNI | MAJOR | Workstream A commits to lifting ~250 lines (`agent_identity.py`) while simultaneously stating that the production fix may be "roughly a one-line re-key" — the difference turns entirely on a hook-payload inspection that has not been done. As written, the interface section reads as a commitment to the module, with the one-line case as an aside. Invert it: make the payload check a precondition that runs before any of A is built, and specify the module and the structured matcher as work that exists only in the branch where the payload carries the parent's path. Otherwise the likely outcome is 250 lines of matcher machinery shipped alongside a re-key that made it unnecessary. |  |  |
| S5 | simplicity/YAGNI | MAJOR | Workstream E does not belong in a design spec and can be deleted from it wholesale. Its own Design-it-twice line says it: "tracker mechanics, with no interface." It contains no design decision, part of it is already executed, and the rest is a confirm-and-close checklist. Carrying it here couples routine backlog hygiene to engineering work with different failure modes and different reviewers, and it inflates the epic so the epic cannot close until tracker chores finish. Move E to a plain checklist Tommy runs, and keep only its one genuine design-adjacent item (filing the unowned resolved-load-manifest finding) as a one-line dependency wherever it is actually a precondition. |  |  |
| S6 | simplicity/YAGNI | MAJOR | Workstream E's item list contradicts itself and duplicates itself, so some of it is already deletable. Issue #336 appears in the already-closed list ("Closed #239, #244, #296, #336, ...") and also in workstream D's list of K1 members that still need to consolidate into a cluster item — it cannot be both. Issues #298 and #322 each appear twice: once in "uncontested close candidates, awaiting explicit confirm" and again as separate bullets under closeout debts ("Verify the epic #298 issue, then close it", "Note #322's settings.json wiring pointer, then close it"). Deduplicate to one line per issue, and correct the K1 membership list. As it stands an executor will do the same close twice and hunt for an issue that is gone. |  |  |
| S7 | simplicity/YAGNI | MAJOR | Workstream C's acceptance test re-proves a premise that exc-8 already proved, once per relocated gate. The two-arm cold-agent tracer answered the question "can an instruction ride the spine channel and be acted on"; running it again for every gate in the tranche does not answer a new question, and a live cold-agent comparison is the most expensive test in the spec. Replace the per-gate tracer with a cheap assertion that the relocated text renders in `current` for that gate, plus one tracer run at the end of the tranche — which is also the run that produces the bulk dose-response data point C says it wants. |  |  |
| S8 | simplicity/YAGNI | MINOR | Workstream B assumes the fix for unrendered `anchors` and `constraints` is to build a renderer, without considering the cheaper fix: delete the fields. The spec establishes that the engine has never rendered them and that agents therefore cannot see them, which means every gate has been driven to date without their content. It does not say how many gates carry these blocks, nor what is in them, nor what breaks if they are removed. Establish that before writing rendering code — if the blocks are vestigial, deleting two schema fields is smaller than adding a projection path and the golden-output tests that guard it. |  |  |
| S9 | simplicity/YAGNI | MINOR | The stale-binding sweeper in workstream A is specified as "ships as a script, runs once, and is kept for reuse" with no second user named. A one-time migration for 47 accumulated bindings, retained indefinitely, becomes a script nobody has run in a year that still has to be understood by the next reader. Either name the recurring condition that calls for it again, or delete the script after the single run and note in the commit that it existed. |  |  |
| S10 | simplicity/YAGNI | MINOR | Workstream F's "paired verbs merge behind an `action` argument" undercuts the reason MCP was chosen. The measured advantage was that typed tools removed fumbles and help-reading that the CLI's subcommand dispatch caused; folding claim/release, block/resume, and record/consolidate behind a string argument rebuilds that dispatch inside the tool, and moves the choice back out of the schema and into prose the model must read. If F survives S1, either give each verb its own tool or drop the tools whose second verb is rare enough to leave on the CLI — the spec already admits the seven-over-eighteen grouping is a placeholder. |  |  |
| S11 | simplicity/YAGNI | MINOR | Three prototype worktrees are retained (`.proto-exc6-...`, `.proto-exc8-...`, `.proto-exc9-...`) as "lift sources," with disposition deferred to the route gate. The spec records a commit SHA for each, which is what makes the code recoverable — the working trees add nothing the commits do not, and retained checkouts on disk with a deferred owner are exactly the debt shape this spec is trying to pay down elsewhere. Delete the worktrees now and cite the SHAs where the lift is described. |  |  |
| S12 | simplicity/YAGNI | MINOR | Several spec sections carry no content a builder can act on and can be deleted outright. "Transcription-grade restoration" states only that it is not applicable. The six per-section approval lines are six copies of the same sentence with the same name and the same date. The "Threshold discipline" section restates grades that are already stated inline in the workstreams that own them. This costs every future reader of the spec, and it dilutes the parts that do carry decisions — a reader skimming for what to build has to sort real constraints out of ceremony. |  |  |
