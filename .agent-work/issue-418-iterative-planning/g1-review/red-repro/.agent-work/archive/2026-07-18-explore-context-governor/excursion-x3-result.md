# Excursion X3 result — agent self-refresh capability across three harnesses

Named question: in each harness, can a running agent cause a FRESH instance of ITSELF to continue its work from within its own execution (true self-refresh), vs (a) spawning a child that returns to a still-full parent, or (b) the layer above / a human restarting it?

## Verdict table

| Harness | Self-refresh CAN/CANNOT | Mechanism or blocking reason | Continuation-child substitute? | Source |
|---|---|---|---|---|
| **Claude Code** (CLI + Agent SDK) | **CANNOT** | Task/subagent tool spawns a child that runs independently and returns a summary to the parent's still-intact context — it never replaces the parent. `--resume`/`--continue` are shell-invoked CLI flags for starting a *new* process; nothing in a running session can call them on itself. Auto-compaction is in-place, harness-triggered summarization within the *same continuous session* (not a fresh instance, and the agent doesn't invoke it — the harness does). The Agent SDK exposes `resume: session_id` as a parameter the **caller's** next `query()` passes in, and hooks (`PreCompact`, `Stop`) fire around loop-state changes but don't let running agent code tear itself down and re-launch. No self-restart API anywhere in the SDK. | Yes — Task/subagent tool (child pattern only) | code.claude.com/docs/en/sub-agents.md; code.claude.com/docs/en/cli-reference.md; code.claude.com/docs/en/agent-sdk/agent-loop.md; code.claude.com/docs/en/agent-sdk/overview.md (via claude-code-guide agent, which has direct doc access; not independently re-fetched by me) |
| **OpenAI Codex CLI** | **CANNOT** | Codex supports subagents (`/agent`, `agents.max_depth` in `~/.codex/agents/*.toml`), explicitly documented as a hierarchical orchestration model: "ChatGPT or Codex handles orchestration across agents, including spawning new subagents, routing follow-up instructions, waiting for results, and closing agent threads," and subagents "return summaries... instead of raw intermediate output" to the parent thread. No documented mechanism for an agent to restart its own session or hand off to a fresh instance of itself — only spawning subordinate children (default max depth 1, i.e. children can't spawn grandchildren). Context is managed via the Responses API's compaction (`context_management` / `/responses/compact`): either automatic server-side compaction when a token threshold is crossed, or an explicit endpoint call — but in both cases it's in-place summarization of the *same* conversation, not termination-and-relaunch, and the "automatic" path needs no agent action while the "explicit" path is a caller-controlled API call, not something documented as agent-self-invoked mid-turn for self-replacement. | Yes — subagent delegation (child pattern only) | developers.openai.com/codex/subagents (redirects to learn.chatgpt.com/docs/agent-configuration/subagents.md); developers.openai.com/api/docs/guides/compaction |
| **pi.dev** | Structurally **CAN** (primitives exist), but the shipped reference behavior is human-triggered, not agent-self-triggered | Pi (by Earendil Inc., MIT-licensed, domain donated by exe.dev; runtime = `@earendil-works/pi-agent-core`) exposes its run loop and session model as a library/extension API, not a closed black box. Concretely: (1) tools can return `terminate: true` in `AfterToolCallResult`, which ends the current agent turn/loop early; (2) the `AgentHarness` extension API exposes `ctx.newSession({ parentSession: ... })`, which creates a new, independent session pre-populated with a generated handoff prompt, linked to the parent session in the on-disk session tree. Pi ships a reference `/handoff` **command** (`examples/extensions/handoff.ts`) built from exactly these two primitives — but as shipped it's registered as a slash command a human types, not a tool the agent calls on itself mid-turn. Because the same primitives (`newSession` + tool-level `terminate` hint) are available to any extension/tool author, an agent-invocable tool that calls `newSession` and returns `terminate: true` would implement genuine self-refresh — the runtime doesn't block it, unlike Claude Code/Codex CLI where no such primitive is exposed to any tool at all. This is a capability distinction (the loop is yours to drive) more than a documented out-of-the-box agent behavior. | Yes, and additionally the harness gives you the raw primitives to build true self-refresh yourself | pi.dev; github.com/earendil-works/pi; github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/handoff.ts; deepwiki.com/earendil-works/pi/2.1-agent-loop-(pi-agent-core) (secondary/unofficial architecture summary — see scope note) |

## pi.dev subscription-billing claim — CONFIRMED

Fred's claim ("pi.dev doesn't work on a Claude subscription") is **confirmed**, with the precise mechanism: pi *can* authenticate via OAuth against a Claude Pro/Max subscription (`/login`, tokens in `~/.pi/agent/auth.json`), so it's not an outright auth block. But Anthropic changed billing policy (reported as effective ~April 4, 2026) so that **third-party-app usage under subscription OAuth draws from a separate "extra usage" pool billed per token, not the subscription's plan limits** — i.e. functionally identical to paying for API access. GitHub issue `earendil-works/pi#3372` ("`pi` can apparently no longer work with Claude subscription") documents this directly, quoting Anthropic's own in-product warning: *"Anthropic subscription auth is active. Third-party usage now draws from extra usage and is billed per token, not your Claude plan limits."* So: technically OAuth-compatible, economically equivalent to API billing — Fred's framing ("doesn't work on a subscription, needs API billing") is accurate in substance. Sources: github.com/earendil-works/pi/issues/3372; github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/providers.md.

## Implication (one line)

A reach-up design (the layer above re-instantiates a fresh agent) works unmodified on all three harnesses today; true self-refresh is not available out-of-the-box on any of them, but pi.dev is the one place it's a genuine near-term bonus, because its run loop and session model are open library primitives (`terminate` tool hint + `newSession`) an agent-invocable tool could be built on — Claude Code and Codex CLI have no equivalent primitive exposed to any tool, agent-invoked or not.
