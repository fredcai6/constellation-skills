**Surfaced by the constellation feedback harvest (2026-06-24).** Two Windows shell hazards keep biting fleets.

### A. PowerShell PR-body / heredoc (story_time, 3× — recurred epic-1 → epic-2)
`powershell-heredoc-use-here-string`: on Windows, bash heredoc for commit messages / PR bodies silently fails. Confirmed that a `gh pr create --body` with a command-substituted heredoc **and** `@'...'@` here-string interpolation **both** fail for PR bodies in PowerShell 5.1 — only `gh pr create -F <file>` / `--body-file` is reliable. Mitigated forward by hand each time, but the shared template doesn't prescribe it, so each fresh fleet rediscovers it.

**Fix:** LAUNCH_ORDER / commander templates hard-prescribe "write the PR body to a temp file and use `gh pr create -F <file>`" on Windows; correct any guidance claiming `@'...'@` here-strings fix PR bodies (they fix `git commit -m`, not `gh pr create --body`).

### B. Engine `command`-checks run under cmd.exe (f1Brainz)
The engine runs `command`-kind postcondition checks via `subprocess(shell=True)` = cmd.exe on Windows. Bash-form checks (`cd '...' && ... | grep -qE`) silently false-FAIL (no `grep`; `&&` semantics differ). Latent — only bites when a check uses pipes / `&&` / POSIX tools; a crew's RED-phase bash checks failed this way and had to be rewritten cmd-safe.

**Fix:** run engine `command` checks under a POSIX shell explicitly, or document that postcondition/handoff commands must be cmd.exe-safe on Windows, and lint plan verification snippets for shell-isms.
